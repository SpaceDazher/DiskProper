# Как работать с MrProper

Спасибо, что хотите помочь. Этот файл — контракт между репозиторием и человеком,
который в него пишет: что нужно поставить, чем проверять правку, какие ворота
должны стать зелёными и чего в issue прикладывать нельзя.

Проект утилиты очистки диска для Windows, поэтому главное свойство правки здесь —
**«ничего лишнего не удалится»**. Всё остальное вторично.

- Спецификация: [`docs/SPEC.md`](docs/SPEC.md). Код обязан соответствовать спеке,
  а не наоборот. Спор о поведении — это спора о тексте §, а не о вкусе.
- Лицензия: MIT ([`LICENSE`](LICENSE)). Репозиторий публичный.
- Уязвимости: **не** через issue — см. [`SECURITY.md`](SECURITY.md).

## Что нужно поставить

| Что | Версия | Зачем |
|---|---|---|
| Visual Studio Build Tools | 2022 (или 2019) с workload **Desktop development with C++** | MSVC: `/W4 /WX`, то есть предупреждение — ошибка |
| CMake | 3.20+ | конфигурация сборки |
| Pester | **4.x** (4.10.1) | e2e-сценарии, см. «Запуск e2e» |
| Git, PowerShell 5.1 | входят в Windows | сценарии и скрипты `tools\` |

Зависимостей у самого MrProper нет: он собирается на голом MSVC, и это проверяемое
свойство, а не случайность этапа 0 ([SPEC §8](docs/SPEC.md)). Сторонние библиотеки
в `CMakeLists.txt` появиться не должны без отдельного решения владельца.

## Сборка и тесты

Единственная разрешённая точка входа — скрипты в `tools\`. Они сами находят
`vcvars64` через `vswhere` и берут замок на компиляцию.

```bat
REM слот — имя каталога сборки (build\<слот>). Обязателен, если вы работаете
REM не одни: без него вы пишете в общий build\main и мешаете соседям.
tools\build.bat Debug a1
tools\test.bat  Debug a1                 :: юнит- и интеграционные тесты
tools\test.bat  Debug a1 unit            :: только юнит-тесты
tools\test.bat  Debug a1 integration     :: только интеграционные
tools\test.bat  Debug a1 unit rules_     :: фильтр по префиксу имени проверки
```

Из WSL то же самое:

```bash
cmd.exe /c "tools\build.bat Debug a1"
cmd.exe /c "tools\test.bat Debug a1"
```

Что означают коды возврата, читайте в выводе: у каждой команды CLI свои коды из
`setsysexits.h` (`0` — успех, `64` — неверные аргументы, `65` — данные не годятся,
`66` — нет входа, `69` — проверка невозможна). Скрипт, который не отличает «отчёт
напечатан» от «набор правил недоступен», врёт.

### Быстрый цикл без e2e

Юнит- и интеграционные тесты закрывают ядро и Win32-обёртки. e2e-сценарии
занимают минуты и запускаются отдельно (см. ниже), а из обычного `ctest` они
выключены меткой:

```bat
cmake -S . -B build\a1
cmake --build build\a1 --config Debug
ctest --test-dir build\a1 -C Debug -LE e2e --output-on-failure
```

## Запуск e2e (сценарии §11 п.3)

Сценарии лежат в [`tests/e2e`](tests/e2e) и проверяют то, чего не проверяют
юнит-тесты: настоящие вызовы `mrproper-cli`, настоящие коды возврата, настоящие
файлы в `%TEMP%`.

```bat
REM Pester 4.x должен быть установлен и указан переменной окружения (см. ниже)
set MRPROPER_PESTER_MODULE=C:\путь\к\Pester\4.10.1\Pester.psd1
ctest --test-dir build\main -C Debug -L e2e --output-on-failure
```

Или напрямую, как это делает автор сценария:

```powershell
Invoke-Pester -Script @{ Path = 'tests\e2e\Test-FullCycle.ps1'; Parameters = @{ Slot = 'a1' } }
```

### Почему нужен Pester 4.x, а не тот, что стоит в Windows

В Windows PowerShell 5.1 из коробки лежит Pester 3.4.0, и сценарии на нём не
идут. Проверено на этой машине:

| Pester | Что происходит |
|---|---|
| 3.4.0 (встроенный) | падает первый блок `Describe`: у него нет ключа `-Tag` (параметр называется `$Tags`) |
| 5.7.1 | падает первая проверка: «Legacy Should syntax (without dashes) is not supported in Pester 5» |
| **4.10.1** | **проходит все формы, которые используют сценарии** |

Установка (PowerShell 5.1, один раз):

```powershell
[Net.ServicePointManager]::SecurityProtocol = 'Tls12'
Save-Module -Name Pester -RequiredVersion 4.10.1 -Path "$env:USERPROFILE\modules" -Force
$env:MRPROPER_PESTER_MODULE = "$env:USERPROFILE\modules\Pester\4.10.1\Pester.psd1"
```

Переменная окружения нужна, чтобы `ctest` и CI импортировали именно 4.x, а не то,
что лежит в системе: в машине могут быть установлены обе версии, и порядок выбора
модулей тогда не наш. `ctest` проверяет версию и падает с внятным текстом, если
модуль не тот, — «прогоняем сценарии» не должно означать «прогоняем их на другой
тестовой платформе».

### Ключ `-Destructive` не передаётся

`Test-FullCycle.ps1` по умолчанию только проверяет инвариант «ничего не удалено» и
пишет в `build\e2e-artifacts\skipped.log`, почему не удалил. Ключ `-Destructive`
разрешает `apply --execute` по кандидатам **настоящего** скана, а на рабочей
машине это её настоящий кэш, а не мусор теста. Ни локальный `ctest`, ни CI его не
передают; на эталонной VM ([SPEC §12](docs/SPEC.md)) прогон с этим ключом делают
руками и отдельным решением.

### Зелёный прогон и пропуски

Сценарии не умеют «пройти на пустом месте»: шаг, который эта сборка выполнить не
может, печатает `SKIPPED: <код> — <текст stderr>`, пишет строку в
`build\e2e-artifacts\*.log` и попадает в сводку. **Зелёный Pester не значит, что
сценарий проверен**: смотрите эти журналы. Критерий §12 «все 20 e2e-сценариев
зелёные» закрывается на эталонной VM, а не на машине сборки.

`New-JunkFixture.ps1` — не сценарий, а генератор фикстур; сам он тестом не
зарегистрирован (в CMake попадают только `Test-*.ps1`).

## Правила очистки: как их менять

Правила — данные, и они решают, что приложение удалит. Поэтому:

1. набор лежит в [`rules/`](rules), это `manifest.json` + `<категория>.json` +
   `rules.sig` (Ed25519, base64);
2. порядок проверки задан [SPEC §9.2](docs/SPEC.md) п.2 и переставлять его нельзя:
   схема манифеста → `minAppVersion` → подпись → SHA-256 и размер каждого файла →
   разбор правил парсером;
3. подписывает набор **владелец приватного ключа**, скриптом
   `tools\sign-rules.ps1`. Приватный ключ в репозиторий не попадает никогда;
4. любая ошибка в цепочке — тихий отказ с записью в лог: приложение продолжает
   работать на предыдущем рабочем наборе и никогда не остаётся без набора правил;
5. проверить набор из командной строки (путь к ключу — свой: публичный ключ
   печатает `tools\sign-rules.ps1 -Action PublicKey`, а в бинарнике он лежит
   константой `core::rules::kRuleSetPublicKey`):

   ```bat
   build\main\Debug\mrproper_cli.exe rules validate rules --json
   build\main\Debug\mrproper_cli.exe rules verify rules --public-key <base64-ключ.txt>
   ```

   `verify` без `--public-key` или без подписи честно отказывает кодом 69:
   «проверять нечем» и «подпись верна» — разные утверждения, и CI обязан их
   различать.

Подкоманды `update` у `rules` нет: обновление из сети выполняет модуль `rulesync`
при запуске приложения (§9.2 п.1), а «проверить сейчас» и «вернуть встроенный
набор» — кнопки в настройках (§9.2 п.5). `rules update` даёт отказ с кодом 69.

## Стиль кода

Планка задана файлами, а не вкусом: `/W4 /WX`, `clang-format` (`.clang-format`),
`clang-tidy` (`.clang-tidy`, любое замечание — ошибка в воротах).

- C++20, `clang-format` перед коммитом, никаких `#pragma warning` и `// NOLINT`
  ради зелёной сборки: предупреждение, которое нельзя починить, — это причина
  переписать место, а не заглушить его;
- имена файлов и команд — как в `src/cli` (`cmd_rules.cpp`, `cmd_rules.hpp`);
- строки в исходниках — UTF-8; **PowerShell-файлы — UTF-8 с BOM** (Windows
  PowerShell 5.1 читает `.ps1` без BOM в ANSI, и русский текст ломает разбор
  файла вплоть до «неожиданный токен»);
- русский текст в CLI идёт в потоки как UTF-8; `getenv` под `/WX` помечен
  устаревшим (C4996) — используйте `_dupenv_s`, как в `tests/harness.hpp`;
- документация кода — в комментариях файла: зачем, а не пересказ строки.

## Ворота приёмки

PR считается закрытым, когда зелёное следующее (`.github/workflows/ci.yml`):

| Job | Что проверяет | Как повторить локально |
|---|---|---|
| `build` | матрица Debug, Debug+ASan/UBSan, Release: сборка и `tools\test.bat` | `tools\build.bat` + `tools\test.bat` для каждой конфигурации |
| `e2e` | сценарии Pester на `windows-latest` | `ctest -L e2e` (нужен Pester 4.x) |
| `ui-smoke` | снимок окна и счёт чернил в трёх раскладках: окно не пустое | `tools\ui-smoke.ps1` (раздел «Ворота интерфейса» ниже) |
| `tidy` | `clang-tidy` по `compile_commands.json`, любое замечание — ошибка | `clang-tidy -p build/tidy --warnings-as-errors=*` |
| `sbom` | CycloneDX-SBOM собранного Release | `anchore/sbom-action`, артефакт прогона |

Проверяются не только тесты, но и `docs\`: критерии §12 человек смотрит по итогам
прогона, поэтому правка документации тоже обязана проходить ворота.

Что именно проверяется критериями §12 (карта дисков, время скана, e2e, отчёт,
права, обновление правил, оформление репозитория) — в
[`docs/SPEC.md`](docs/SPEC.md), раздел 12.

## Ворота интерфейса: «окно не пустое»

Сборка и линковка ничего не говорят о том, что человек увидит. Так уже
случилось: приложение запускалось, закрывалось с кодом 0, а клиентская область
была однородной заливкой — ни рельса, ни одного из пяти экранов. Проверка
`tools\ui-smoke.ps1` (job `ui-smoke`) снимает окно через `PrintWindow` и считает
пиксели, отличные от фона, в двух областях: во всей клиентской и в окне
содержимого (дочернем окне справа от рельса).

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 `
    -Exe build\a1\src\ui\Debug\mrproper.exe -Width 1280 -Height 720 `
    -ThemeMode dark -ExpectBackground dark -Shot D:\Temp\ui-1280x720.png
echo %ERRORLEVEL%
```

Обвязка `-ThemeMode`/`-ExpectBackground` пишет **свой** ключ приложения
`HKCU\Software\MrProper\UI\ThemeMode` и возвращает прежнее значение; системную
тему `Personalize\AppsUseLightTheme` скрипт не трогает — это настройка машины,
а не приложения.

### Коды возврата

| Код | Что означает | Что делать |
|---|---|---|
| `0` | окно нарисовало содержимое: есть чернила и в клиентской области, и в окне содержимого | ничего, это зелёные ворота |
| `2` | неверные аргументы (`-Width` без `-Height`, неизвестный `-ThemeMode`, отрицательный порог) | исправить команду |
| `3` | окно не приняло запрошенный размер или DPI, либо к моменту съёмки окно оказалось свёрнутым и имеет размер меньше 200×200 | проверить `layoutContentHost` и `WM_GETMINMAXINFO` |
| `4` | клиентская область пустая: только фон, чернил меньше `-MinInkPixels` (по умолчанию 2000) | интерфейс не нарисован вовсе |
| `5` | окно не создано: `EnumWindows` не нашло у процесса видимого окна больше 200×200 с заголовком | смотреть, дошло ли дело до `WM_CREATE` |
| `6` | процесса нет, бинарника нет или процесс упал | сначала починить сборку или запуск |
| `7` | среда не подготовлена: реестр недоступен или не восстановился прежний `ThemeMode` | проверить права на `HKCU\Software\MrProper` |
| `8` | фон не соответствует ожидаемой теме (светлота по WCAG вне 0.03…0.50) | палитра пришла из константы, а не из темы |
| `9` | окно содержимого пустое: рельс нарисован, а внутри окна содержимого меньше `-MinContentInkPixels` (5000) чернил, меньше `-MinContentColors` (4) разных цветов или меньше `-MinCenterInkPixels` (250) чернил в центральных 70 % | экран не отрисован в хосте содержимого |

Код `0` означает ровно одно: **в окне содержимого есть нарисованный экран**. Рельс
навигации рисует оболочка всегда, поэтому одного «процесс жив» и одного «окно
больше 200×200» мало — так проходит и пустое окно.

### Как смотреть снимок

Снимок по умолчанию — `D:\Temp\mrproper-window.png`, в CI он кладётся
артефактом `ui-smoke-shots` (файлы `ui-window-1280x720.png`,
`ui-window-1920x1080.png`, `ui-window-150dpi.png` и `ui-smoke.log`). Код говорит,
**сколько** нарисовано; снимок говорит, **что** нарисовано. Открывайте его
глазами при каждом падении ворот: у пустого содержимого это однородная заливка
цветом окна, у обрезанного — белая полоса вдоль края, у неcontrastного — текст
цветом фона.

Признаки, которые ворота ловят числами:

* рельс нарисован, содержимое пустое — `чернила=37296` в клиенте (17,72 % при
  1280×720) и `чернила=0` в окне содержимого → код `9`;
* окно содержимого на 19 пикселей выше клиентской области, и его
  неприпаркованная полоса видна снизу и справа — 13152 «чернила», но всего
  **2** цвета → код `9` по числу цветов (нарисованный экран даёт 7…9 даже без
  ClearType, пустой хост — 1);
* при 150 % DPI окно содержимого съезжает влево и накрывает правый край рельса:
  7590 «чернил» и 7 цветов из подписей рельса дали бы код `0`, а в центральных
  70 % того же окна 0 чернил → код `9` по центру;
* окно схлопнулось в иконку 160×24, пока ждали перерисовку, — код `3`, а не
  «фон не тот» (раньше это давало код `8` и снимок 160×24).

### Раскладки, которые проверяются

Ворота гоняют три раскладки, и это не «на всякий случай»:

```powershell
-Width 1280 -Height 720                      :: 1280x720 логических пикселей
-Width 1920 -Height 1080                     :: 1920x1080 логических пикселей
-Width 1280 -Height 720 -DpiPercent 150      :: то же при 150 %: окно 1920x1080 физических
```

`-Width`/`-Height` заданы в логических пикселях (DIP, 96 DPI = 1.0).
`-DpiPercent` не меняет масштаб экрана (это требует прав администратора и выхода
из сеанса), а шлёт окну `WM_DPICHANGED_AFTERPARENT` — то самое сообщение,
которым Windows в режиме per-monitor v2 сообщает смену DPI, — и требует, чтобы
минимум окна, объявленный самим приложением (`WM_GETMINMAXINFO`), вырос ровно
в `effDpi/96` раз. Проверено: `900x600 → 1350x900` при dpi 144.

Прав администратора ворота не требуют: приложение только рисует окно, состояние
темы готовится в `HKCU` собственного ключа.

### Тема и язык

Проверка «цвета берутся из темы, а не из констант» — это пара ключей
`-ThemeMode` + `-ExpectBackground`. Скрипт не переключает тему Windows: он пишет
`ThemeMode` приложения, ждёт окно и сравнивает **светлоту самого частого цвета**
в клиентской области с формулой WCAG. Границы 0.03 и 0.50 разведены в 16 раз,
крайние палитры дают 0.013 (тёмная `0x20`) и 0.896 (светлая `0xF3`) — обе
проходят, «средняя» серая палитра не проходит ни одну.

Проверка не зависит от языка: она считает пиксели и не читает ни одной строки
текста, поэтому окно с английскими подписями даёт тот же результат, что и с
русскими. Язык приложения берётся из `GetUserDefaultUILanguage`, так что на
англоязычном раннере ворота ведут себя так же.

## Issue и pull request

Шаблоны — [`.github/ISSUE_TEMPLATE/bug.yml`](.github/ISSUE_TEMPLATE/bug.yml) и
[`.github/ISSUE_TEMPLATE/feature.yml`](.github/ISSUE_TEMPLATE/feature.yml); они
двуязычные (русский и английский), потому что так же двуязычен сам продукт
(SPEC §5 «Локализация»).

**Не прикладывайте отчёты и дампы «как есть».** Даже случайный отчёт содержит
приватные данные: серийники дисков и модели, ваши личные каталоги
(`Downloads`, профили, сетевые пути), а в отчёте есть пути. Перед отправкой
замаскируйте серийники, если для разбора они не нужны. Подробности и список
приоритетных дефектов — в [`SECURITY.md`](SECURITY.md).

Об уязвимостях (в том числе о дефектах, из-за которых можно удалить чужие данные)
публичный issue заводить нельзя — там же написано, как сообщать приватно.

## Право на «нет»

Не все пробелы в спеке закрываются кодом. Если правка требует решения владельца
(интерфейс, политика удаления, ключ подписи), опишите проблему в issue и
предложите варианты — это быстрее, чем реализация, которую придётся переделывать.
