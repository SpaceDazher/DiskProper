# Ключ подписи набора правил

Рабочее описание ключа Ed25519 и скрипта `tools/sign-rules.ps1` из SPEC §9.2
(ADR-008). Ключ подписывает набор правил очистки, а правила управляют тем, что
приложение удаляет, поэтому к этому файлу относятся так же строго, как к коду
движка удаления.

Короткое резюме: приватная половина ключа создаётся один раз, живёт офлайн вне
репозитория и никогда не коммитится; публичная половина — обычная константа в
исходниках, она ревьюится как код; подписывает набор скрипт вручную или
self-hosted раннер, секрет в репозитории или в CI не хранится.

## 1. Что чем подписано

| Объект | Что это | Правило |
| --- | --- | --- |
| `rules/manifest.json` | манифест набора: версия, `minAppVersion`, список файлов с SHA-256 и размером | подписываются **байты файла как есть**, без переформатирования и перекодировки |
| `rules/rules.sig` | подпись Ed25519 манифеста | **88 символов** base64 от 64 сырых байт (`R` 32 байта + `S` 32 байта), UTF-8 без BOM, без перевода строки |
| `core::rules::kRuleSetPublicKey` | публичный ключ, встроенный в бинарник | ровно **32 сырых байта**, base64 от них — то, что печатает `-Action NewKey` |

Подписывается манифест, а не каждый файл: манифест уже фиксирует SHA-256 и
размер каждого файла, поэтому подпись манифеста покрывает весь набор
транзитивно. Проверка файлов идёт после проверки подписи — так же, как описано
в SPEC §9.2 п.2 и реализовано в `src/core/rulesync.cpp`
(`parseManifest` → `minAppVersion` → подпись → SHA-256/размер → разбор правил).

Порядок не переставляется: подпись проверяется раньше хешей, а файл, не
перечисленный в манифесте, — отказ (в ядре это `requireKnownFilesOnly`).
Набор, который приложение всё равно отвергнет, подписывать нельзя, поэтому
`-Action Sign` сначала сверяет манифест с фактическими файлами и только потом
подписывает.

Путь к файлу подписи по умолчанию — `rules\rules.sig`, рядом с манифестом: так
набор версионируется одним каталогом (дерево репозитория в SPEC §9.1 относит
подпись к `rules\`). Если `rulesync` будет брать подпись из корня репозитория,
путь задаётся параметром `-SignaturePath`, а в `.gitignore` добавляется
`/rules.sig`, иначе подпись попадёт в коммит случайно.

## 2. Где живёт приватный ключ

Путь по умолчанию: `%USERPROFILE%\.mrproper\rules-ed25519.key` — то есть вне
репозитория и вне `%LOCALAPPDATA%\MrProper`, где приложение держит рабочий набор
правил. Другой путь задаётся параметром `-KeyPath`; ключ, оказавшийся внутри
репозитория, скрипт отвергает (код возврата 2) — правило «приватная часть
никогда не попадает в репозиторий» проверяется механически, а не по договорённости.

В `.gitignore` есть записи `rules/*.key`, `rules/*.pem`, `rules/private-*` —
это второй рубеж на случай, если ключ положат не туда. Первый рубеж — отказ
самого скрипта.

Файл ключа устроен так:

| Смещение | Размер | Содержимое |
| --- | --- | --- |
| 0 | 8 | `MRPRK1\0\0` — сигнатура, по ней файл отличается от мусора |
| 8 | 32 | публичный ключ (не секрет: нужен, чтобы ключ был самодостаточным и чтобы подсунуть файл с чужим seed было нельзя) |
| 40 | … | seed (32 байта), зашифрованный **DPAPI, CurrentUser**, с энтропией `MrProper rules signing key v1` |

Права на файл скрипт сужает до владельца через `icacls`; если `icacls`
недоступен, об этом печатается предупреждение, а не делается вид, что файл
закрыт.

Из этого следуют два ограничения, о которых надо знать заранее:

* **DPAPI-привязка.** Ключ расшифровывается только под той учётной записью и на
  той машине, где он создан. Копия ключа на другую машину или под другую учётную
  запись бесполезна — нужен безопасный канал передачи или новая пара ключей.
  На self-hosted раннере это обычно отдельная машина и отдельная учётная запись,
  что как раз и нужно.
* **Пароля нет.** Скрипт не спрашивает пароль и не хранит его: секрет
  защищается учётной записью Windows, а не ещё одним строкым вводом.

## 3. Рабочий цикл

Шаги выполняются один раз и повторяются при каждом изменении набора правил.

1. **Создать ключ** (один раз на машину):

   ```cmd
   tools\sign-rules.ps1 -Action NewKey
   ```

   Скрипт напечатает публичный ключ в трёх видах: base64, hex и готовый
   фрагмент `inline constexpr std::uint8_t kRuleSetPublicKey[32] = { … }`.

2. **Вставить публичный ключ в исходники** — константой
   `core::rules::kRuleSetPublicKey` (SPEC §9.2), и пересобрать приложение.
   Публичный ключ коммитится: он и должен ревьюиться как код.

3. **Подписать набор**:

   ```cmd
   tools\sign-rules.ps1 -Action Sign -AppVersion 1.0.0
   ```

   Скрипт проверит, что манифест сходится с файлами, подпишет его и запишет
   `rules/rules.sig`. Ничего не сошлось — файл подписи не создаётся вовсе.

4. **Проверить набор** (то же, что делает приложение, но без сборки):

   ```cmd
   tools\sign-rules.ps1 -Action Verify -AppVersion 1.0.0
   ```

5. **Опубликовать** набор и подпись по тегу `rules/vX.Y`: приложение
   спрашивает `manifest.json` и `rules.sig` по HTTPS с пином тега (SPEC §9.2
   п.1). Подпись без манифеста, манифест без подписи и файлы не из манифеста —
   приложение отвергает.

Перед первым использованием и после любой правки скрипта:

```cmd
tools\sign-rules.ps1 -Action SelfTest
```

`SelfTest` прогоняет эталонные векторы RFC 8032 §7.1 (пустое сообщение,
`0x72`, `0xaf82`), проверяет, что подделка под сообщение и подпись чужим ключом
не проходят, и возвращает ненулевой код при любом расхождении. Реализация
Ed25519 встроена в скрипт, потому что штатный Windows PowerShell 5.1 работает на
.NET Framework 4.x, где Ed25519 нет ни в CNG, ни в `System.Security.Cryptography`.
Модуль, который подписывает правила удаления, не вправе молча доверять собственной
криптографии — та же мысль, что `sha256SelfTest` в ядре.

## 4. Действия и коды возврата

| Действие | Что делает | Пишет на диск |
| --- | --- | --- |
| `NewKey` | генерирует пару Ed25519, шифрует seed через DPAPI, печатает публичный ключ | файл ключа |
| `Sign` | сверяет манифест с файлами, подписывает байты манифеста, сверяет и перечитывает записанный файл | `rules/rules.sig` |
| `Verify` | проверяет подпись манифеста, `minAppVersion`, SHA-256 и размер каждого файла, отсутствие лишних файлов | ничего |
| `CheckManifest` | только сверка манифеста с файлами, без ключа | ничего |
| `PublicKey` | печатает публичный ключ из файла ключа | ничего |
| `SelfTest` | векторы RFC 8032 плюс отрицательные проверки | ничего |

Коды возврата: `0` — успех, `1` — проверка не пройдена (набор не подписан,
подпись или хеши не сошлись, ключа нет), `2` — ошибка использования или
окружения (ключ внутри репозитория, неизвестный ключ, Add-Type не собрал Ed25519).

Параметры: `-RepoRoot`, `-RulesDir`, `-ManifestPath`, `-SignaturePath`,
`-KeyPath`, `-PublicKeyBase64`, `-AppVersion`, `-AllowUnlisted`, `-Force`,
`-Json`, `-Quiet`. Значения по умолчанию: репозиторий — родитель `tools\`,
набор — `rules\`, манифест — `rules\manifest.json`, подпись — `rules\rules.sig`,
ключ — `%USERPROFILE%\.mrproper\rules-ed25519.key`.

`-AllowUnlisted` существует только для отладки: он разрешает файл `*.json` в
каталоге набора, не перечисленный в манифесте, но приложение такой набор всё
равно отвергнет, поэтому подписанный с ним набор бесполезен.

## 5. Проверка в CI

Скрипт ничего не знает про CI и не требует ничего, кроме PowerShell 5.1.
Секрет в репозитории не хранится: подписание живёт на self-hosted раннере, у
которого есть и ключ, и учётная запись, его расшифровывающая.

```yaml
# .github/workflows/sign-rules.yml — только self-hosted раннер
jobs:
  sign:
    runs-on: [self-hosted, windows]        # публичные раннеры ключа не имеют
    steps:
      - uses: actions/checkout@v4
      - name: самопроверка Ed25519
        shell: powershell
        run: tools\sign-rules.ps1 -Action SelfTest
      - name: проверка набора
        shell: powershell
        run: tools\sign-rules.ps1 -Action CheckManifest -AppVersion 1.0.0
      - name: подпись
        shell: powershell
        run: tools\sign-rules.ps1 -Action Sign -AppVersion 1.0.0
```

С `-Json` на stdout печатается ровно один JSON-объект, а человекочитаемый отчёт
уходит в stderr — так вывод разбирается в CI без фильтрации:

```cmd
tools\sign-rules.ps1 -Action Verify -PublicKeyBase64 "i/qkJk/0FY…" -AppVersion 1.0.0 -Json
:: {"action":"Verify","ok":true,"version":"2026.09.1","signatureOk":true,"checked":24,"problems":[]}
```

Не-ASCII в JSON записан escape-последовательностями, поэтому строка читается в
любой кодировке консоли.

## 6. Что обязано совпасть с приёмной стороной

`rulesync` проверяет подпись сам, и скрипт — не второй источник правды, а
инструмент владельца. Расхождение в любом из этих пунктов даст «подпись не
сошлась» на ровном наборе:

1. Подписываются **байты `manifest.json`**, а не его разобранная структура и не
   канонизированный JSON. Любая пересборка манифеста меняет подпись.
2. Подпись — **64 сырых байта**, записанные в файл как base64; при чтении
   пробельные символы по краям отбрасываются.
3. Публичный ключ — **32 сырых байта**. Хранить его можно как есть, как hex или
   как base64 — на входе проверки ожидаются 32 байта.
4. Уравнение проверки: `[S]B == R + [k]A` при `0 <= S < L`, `k = SHA-512(R‖A‖M) mod L`
   (RFC 8032, без кофактора). Подпись в формате `ssh-keygen -Y sign` для этого
   не годится: там лишняя SSHSIG-обёртка.
5. Хеш файла — SHA-256 от байтов файла, строчными hex-символами; размер
   сверяется, если объявлен.

## 7. Ротация ключа и компрометация

Обычный цикл: правила меняются часто, ключ — нет. Пока приложение доверяет текущему
публичному ключу, менять его незачем.

Когда менять приходится:

1. Создать новую пару (`-Action NewKey` в другом месте или с `-Force`), вставить
   новый публичный ключ в исходники и выпустить релиз.
2. Поднять `minAppVersion` в манифесте до версии этого релиза: старые сборки
   перестанут принимать новый набор, а новые — принимать старый. Пока
   `minAppVersion` не поднят, скомпрометированный ключ остаётся действующим для
   всех, кто ещё не обновился.
3. Переподписать набор новым ключом, опубликовать по тегу `rules/vX.Y`.

Если приватный ключ утек — тот же порядок, но без «постепенно»: подпись,
выданная скомпрометированным ключом, для новых сборок недействительна сразу, а
приложение на старом наборе продолжит работать (откат, а не отказ, SPEC §9.2
п.4). О факте компрометации стоит написать в `SECURITY.md` репозитория: публичный
репозиторий и подпись правил удаления — тот случай, когда молчание дороже.

Отозвать старый набор без смены ключа нельзя: подпись Ed25519 не имеет срока
действия, единственный рычаг — публичный ключ в бинарнике плюс `minAppVersion`.

## 8. Чего скрипт не делает

* Не генерирует и не правит `manifest.json`: манифест — данные набора, и его
  формат задаёт ядро (`parseManifest`). Скрипт только проверяет, что манифест
  сходится с файлами.
* Не скачивает набор и не ходит в сеть. Подписывается то, что уже лежит в
  `rules\`.
* Не коммитит и не тегирует: коммитит оркестратор репозитория.
* Не знает, что было в предыдущем наборе, и не откатывает ничего: откат —
  задача приложения (SPEC §9.2 п.4).
* Не хранит пароль и не спрашивает его.

## 9. Проверка на своей машине

```cmd
tools\sign-rules.ps1 -Action SelfTest                       :: векторы RFC 8032
tools\sign-rules.ps1 -Action CheckManifest -AppVersion 0.1.0 :: набор цел
tools\sign-rules.ps1 -Action Sign -AppVersion 0.1.0         :: подпись
tools\sign-rules.ps1 -Action Verify -AppVersion 0.1.0       :: подпись и хеши
```

Скрипт лежит в UTF-8 **с BOM** и с CRLF — не из вкуса, а по двум причинам:
Windows PowerShell 5.1 читает файл без BOM в однобайтовой кодировке консоли,
где русские «ёлочки» превращаются в кавычки и ломают разбор скрипта; CRLF
потребовают `cmd.exe`, PowerShell и git с `autocrlf=true` (`.editorconfig`).
