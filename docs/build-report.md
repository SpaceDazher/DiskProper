### 3.2 Интеграционные тесты Win32-слоя

**Методологического замечания, которое было, больше нет.** На момент прогона задачи 98
`tools\test.bat` запускал только `mrproper_unit_tests.exe`, и 11 провалов были не видны
ни в одном вороте. Исправлено в `90d5032`: скрипт получил параметры `suite` и `prefix`
и теперь гоняет **оба** набора. Ниже — то, что наконец видно.

```
== MrProper integration ==
  [FAIL] vfsEdge_longPath_delete_inside_root_and_refuses_outside
         tests\integration\vfs_edge_tests.cpp:603
  [FAIL] vfsEdge_unicode_names_survive_round_trip
         tests\integration\vfs_edge_tests.cpp:746
  [FAIL] vfsEdge_reparse_junction_is_reported_but_not_followed
         tests\integration\vfs_edge_tests.cpp:857
FAIL: 25 проверок, провалов 3
```

Было 11 провалов из 25 (Release, `a98`), стало 3 (Debug, `a7`). Улучшение относится к
незакоммиченной правке обхода ФС параллельной задачи, а не к волне починки, и один новый
провал прибавился: `vfsEdge_reparse_junction_is_reported_but_not_followed` падает на
`CHECK(!summary.complete())` — обход доходит дальше прежнего и честно останавливается
там, где раньше останавливался раньше.

Помимо провалов в выводе есть одно пропущенное по среде и восемь предупреждений:

```
  [skip] trash_boundary_junctionInsideRootLeavesOutsideDataIntact:
         точка монтирования не создана: ... (4392)
  [warn] не удалось убрать фикстуру C:\Users\Daniil\AppData\Local\Temp\MrProper-it-7452-N   (8 штук)
```

4392 — `ERROR_INVALID_REPARSE_DATA`: создать junction в каталоге фикстуры не вышло,
то есть **эта проверка границы обхода сегодня не выполнена** (вторая, с тем же названием
и другим способом, зелёная). Предупреждения об уборке фикстур — не провал проверки,
но оставляют мусор в `%TEMP%`.

**Владелец этих файлов — параллельная задача**, и правило 1 запрещает их трогать,
поэтому разбора трёх провалов в этом отчёте нет.

## 7. Как повторить

Из корня репозитория, слот — свой (обязательный, иначе агенты делят кэш CMake):

```
tools\build.bat Debug a7
tools\test.bat Debug a7
```

Критерий задачи одной строкой (это именно та команда, которой зафиксирован вердикт):

```
tools\test.bat Debug a7
```

Для повторения прогона конфигурации `Release` (с числами §4) слот прежний:

```
tools\build.bat Release a98
tools\test.bat Release a98
```

E2E — отдельным шагом, в ворота они не входят и в критерий задачи не входят:

```
Invoke-Pester -Script @{ Path = 'tests\e2e\Test-*.ps1';
                        Parameters = @{ Configuration = 'Debug'; Slot = 'a7' } }
```

Сценарий можно фильтровать по одному файлу, чтобы уложиться в разумное время на
конфигурации `Debug`: на Release весь набор шёл 253 с, на Debug — не уложился.

Логи прогона задачи 98, оставленные в сборочном каталоге (в `.gitignore`, репозиторию
не мешают):

| Файл | Что в нём |
|---|---|
| `build\a98_run1.log` | чистая сборка Release с нуля, отчёт конфигурации CMake |
| `build\a98_final.log` | критерий задачи: `build && test` одной командой |
| `build\a98_test_timed.log` | юнит-тесты с замером wall-clock |
| `build\a98_integration.log` | интеграционные тесты Release (11 провалов) |
| `build\a98_base_integration.log` | контрольный прогон бинарника базы `build\main\Debug` (12 провалов) |
| `build\a98_e2e_fullcycle.log`, `build\a98_e2e_rest.log` | e2e, Pester |

Логи прогона F7 в репозиторий не кладутся: слот `a7` и его содержимое — во
внутреннем `.bb`-хранилище волны, а `build/` в `.gitignore`.
