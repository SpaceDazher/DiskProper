# SPEC — «MrProper»: десктоп-приложение для Windows (инвентаризация дисков + умная очистка)

Статус: v1.0 — открытые вопросы закрыты (см. §13) · Платформа: Windows 10 22H2 / Windows 11, x64 · Стек: C++20, Win32 + Direct2D/DirectWrite, CMake + MSVC 2022 (v143) · Репозиторий: публичный · Распространение: неподписанные сборки, личное использование

---

## 1. Краткое резюме

Приложение для Windows, которое:

1. **Собирает полную картину по дискам** — все физические диски, все разделы (GPT/MBR), все тома, точки монтирования, файловые системы, шифрование, модель/серийник/интерфейс, наличие TRIM и SMART.
2. **Показывает, что можно освободить** — сканирует системные и пользовательские каталоги, кэши приложений и браузеров, корзину, логи, дампы; измеряет реальный размер (аллоцированный и логический), возраст, признаки использования.
3. **Предлагает варианты очистки** — каждый кандидат приходит с категорией, оценкой риска, объяснением («почему это мусор»), ожидаемым освобождением и уровнем доверия. Решения скрыты/выбраны по умолчанию осознанно, а не «всё подчистить».
4. **Выполняет очистку безопасно и обратимо** — план действий, dry-run, собственная корзина с журналом, отмена, отчёт.

Продуктовая идея отличия от «просто чистилки»: **разделить сбор данных (полно, дёшево) и принятие решений (консервативно, объяснимо, откатываемо)**. Здоровье носителя (SMART/NVMe) — модуль, заложенный в архитектуре, входящий в v1.1 (решение владельца, §13).

### 1.1 Профиль пользователя и продукта

- **Кто:** владелец домашнего ПК (Windows 10/11, x64, без домена и групповой политики). Утилита «для себя», но репозиторий публичный — значит, чужие глаза на коде тоже будут.
- **Сценарий:** «диск заполнился» или «хочу понять, что занимает место и что безопасно выкинуть».
- **Приоритеты (по убыванию):** безопасность данных → понятность объяснений → обратимость → скорость → внешний вид.
- **Что из этого следует:**
  - CLI (`mrproper-cli`) — инструмент разработчика, CI и e2e, а не пользовательский интерфейс; отдельной пользовательской функциональности для него не проектируем.
  - Не нужны: GPO/AD, централизованные политики, корпоративный SSO, телеметрия, админский аудит-лог. Локализации ru + en достаточно.
  - Онбординг важнее блестящего интерфейса: первый запуск обязан объяснить, что будет удалено, и предложить безопасный профиль по умолчанию.
  - Установка без подписи кода: SmartScreen может предупредить — это ожидаемо и описано в README (ADR-009).

## 2. Цели и критерии успеха

| # | Цель | Как измеряем |
|---|---|---|
| G1 | Пользователь видит полную карту разделов без установки сторонних утилит | Скриншот-эталон: 100 % дисков/разделов в системе отображены, включая скрытые разделы без букв |
| G2 | Приложение само находит освобождаемое место | Полный скан системного диска: на тестовой VM — ≥ 1 ГБ кандидатов, все с подтверждённым путём |
| G3 | Очистка ничего не ломает | 0 инцидентов на регрессионном прогоне (20 сценариев); 100 % удалённых файлов восстанавливаются из корзины приложения |
| G4 | Понятная цена решения | Каждый кандидат имеет категорию, оценку риска, причину и ожидаемое освобождение — 0 кандидатов «без объяснения» |
| G5 | Быстро | Полное сканирование C: на SSD ≤ 60 с; старт приложения ≤ 1 с; idle по CPU ≤ 2 %, по памяти ≤ 150 МБ |

**Не-цели (MVP):** реестр, автозагрузка, удаление программ, дефрагментация/анализ поверхности, SMART, планировщик, учётные записи/облако. Правила очистки обновляются с публичного GitHub-репозитория — это не «облако» и не аккаунт, а скачивание подписанного набора файлов (§9.2).

## 4. Функциональные требования MVP

### FR-1. Сбор данных по дискам (инвентаризация)

Источники данных, в порядке использования:

1. **Физические диски**: `SetupDiGetClassDevsW(GUID_DEVINTERFACE_DISK)` + `SetupDiEnumDeviceInterfaces` + `SetupDiGetDeviceInterfaceDetailW` → device path вида `\\?\X#&…` (к device path добавляется завершающий `\`), затем `IOCTL_STORAGE_GET_DEVICE_NUMBER` для номера и типа.
2. **Модель, серийник, прошивка, тип шины**: `IOCTL_STORAGE_QUERY_PROPERTY` со свойствами `StorageDeviceProperty`, `StorageDeviceIdProperty`, `StorageAdapterProperty` (`STORAGE_ADAPTER_DESCRIPTOR` → `BusType`: NVMe=0x11, SATA/ATA, SCSI, USB). Дополнительно: `StorageDeviceWriteCacheProperty`, `StorageDeviceTrimProperty`, `StorageDeviceLBProvisioningProperty`, `StorageDeviceIoCapabilityProperty`.
3. **Размер диска**: `IOCTL_DISK_GET_LENGTH_INFO` на `\\.\PhysicalDriveN` (открывается с `GENERIC_READ|GENERIC_WRITE`).
4. **Разметка и разделы**: `IOCTL_DISK_GET_DRIVE_LAYOUT_EX` (`DRIVE_LAYOUT_INFORMATION_EX`) — смещение, длина, тип MBR-раздела или GPT-GUID, GPT-атрибуты, GPT-имя раздела.
5. **Тома и привязка к дискам**: `FindFirstVolumeW/FindNextVolumeW` для `\\?\Volume{GUID}\`, `FindFirstVolumeMountPointW` для точек монтирования (в т. ч. папки), `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` (`VOLUME_DISK_EXTENTS`) — привязка тома к диску и смещению (важно для динамических/спанных томов и RAID).
6. **Файловая система, метка, флаги, свободное место**: `GetVolumeInformationW` (`GetVolumeInformationByHandleW` — надёжнее), `GetDiskFreeSpaceExW`.
7. **Шифрование**: WMI `Win32_EncryptVolume.EncryptState`; fallback — `manage-bde -status`. `FltGetEncryptionVolumeInfo` отклонён (требует minifilter-драйвера).
8. **Дополнительно (WMI, только при необходимости)**: `MSFT_PhysicalDisk`, `MSFT_Volume`, `Win32_DiskDrive`, `MSFT_StorageFault` — обогащение и проверка согласованности с IOCTL-картиной.

Требования к результату: обход всех дисков за один проход, устойчивость к «отказавшим» дискам (таймаут 2 с на устройство, устройство помечается недоступным, приложение не падает), результат кэшируется и перечитывается по событию `WM_DEVICECHANGE`.

### FR-2. Экран «Диски» (карта разделов)

- Дерево: физический диск → разделы → тома (буквы, mount points, label).
- Для каждого узла: размер, занято/свободно, ФС, разряд GPT/MBR, тип раздела (системный, загрузочный, MSR, Recovery, OEM, EFI, Basic Data), шифрование, removable, TRIM, модель/интерфейс, серийник, температура (если есть провайдер).
- Визуализация: горизонтальные полосы пропорционально размеру, вложенность «диск → разделы» видна визуально; клик по разделу — карточка с деталями и кнопкой «Открыть в проводнике» / «Проверить» (в v1.1).
- Экспорт карты в JSON и в текст (для баг-репортов).
- Сортировка, фильтр «только с буквами / только системные / removable».

### FR-4. Оценка кандидатов (это и есть «умная» часть)

Каждый кандидат получает:

- `LogicalBytes` и `AllocatedBytes` (освобождаемое место считаем по **аллоцированному** размеру, т.к. free space изменяется им).
- `NewestWrite`, `OldestWrite`, `LastAccess` (если файловая система их отдаёт), число файлов.
- **SafetyLevel**: `Safe` / `Review` / `Risky`. `Risky` скрыт по умолчанию (показать можно только через «показать все», с подтверждением).
- **ConfidenceScore** (0–100): насколько уверены, что это безопасно. Снижают: неизвестный путь, нет правила, файл создан сегодня, файл в пользовательских данных, совпадение с белым списком приложений.
- **Reasons**: человекочитаемое объяснение («кэш браузера Edge, профиль Default, 2 145 файлов, старше 30 дней; приложение не запущено»).
- **LockedBy**: процессы, удерживающие файлы (Restart Manager: `RmStartSession` → `RmRegisterResources` → `RmGetList`).

Правила — **данные, а не код**: JSON-схема правил, поставляется с приложением, обновляется без пересборки.

```json
{
  "id": "browser.cache.edge",
  "category": "browser.cache",
  "safety": "safe",
  "locator": "%LOCALAPPDATA%\\Microsoft\\Edge\\User Data\\*\\Cache\\**",
  "locatorExcludes": ["**/Service Worker/ScriptCache/**"],
  "minAgeDays": 0,
  "requiresProcessesClosed": ["msedge"],
  "groupBy": "profile",
  "title": {"ru": "Кэш Microsoft Edge", "en": "Microsoft Edge cache"}
}
```

### FR-5. План очистки

- Экран «Очистка»: дерево категорий → элементы, с чекбоксами и агрегатами (сколько всего освободим, если выбрать всё / только Safe / только выбранное).
- **Dry-run обязателен** и запускается по умолчанию перед первым удалением в сессии: показывает точный список операций.
- Каждое действие: `Delete` (прямое удаление), `Trash` (в корзину приложения), `Keep`, `Skip (locked)`.
- Перед исполнением — снимок состояния: список операций, PID, версия, размер; запись в журнал.

### FR-6. Исполнение

- Фоновые потоки (пул), отмена через `CancellationToken` (событие + atomic), прогресс — через колбэк в UI-поток (маршалинг `PostMessage`).
- Защита от «съедания» чужих данных:
  - пропуск reparse points (symlink/junction) — защита от петель и выхода за пределы пути;
  - нормализация путей через `GetFinalPathNameByHandleW` (снимает 8.3 и разрешает reparse), поддержка `\\?\` для путей > MAX_PATH;
  - белый список защищённых каталогов (Windows, Program Files, System Volume Information) — правило запрета на уровне движка;
  - проверка, что путь внутри ожидаемого корня правила.
- Блокировки: определение через Restart Manager, опция «закрыть эти приложения» (`RmShutdown`) с подтверждением; повтор с backoff 3×.
- Ошибки не фатальны: собираются в отчёт, остальные операции продолжаются.

### FR-7. Корзина приложения и отмена

- Своя корзина: `%ProgramData%\MrProper\Trash\<txId>\` + `manifest.json` (исходный путь, размер, mtime, ACL).
- Ограничения: по умолчанию ≤ 2 ГБ и ≤ 7 дней; для больших кэшей (> 100 МБ) — прямое удаление с записью в журнал (иначе корзина раздувается).
- Кросс-томовое перемещение = копирование: честно показываем «это займёт время», большие транзакции предлагаем сразу прямой делет.
- Восстановление: полное или частичное (по элементу), проверка конфликтов (существующий файл — не перезаписывать, спросить).

### FR-8. Отчёт

- Экспорт: HTML (человекочитаемый), JSON (машиночитаемый), текстовый дамп (для баг-репортов).
- Содержит: карту разделов, список кандидатов с оценками, список выполненных операций, ошибки, время, версии ОС/приложения.
- Отчёт пишется в `%LOCALAPPDATA%\MrProper\reports\`, с ограничением количества файлов (последние 20).

### FR-9. Настройки и политики

- Правила вкл/выкл, смена safety-уровня для конкретного правила (с двойным подтверждением для Risky).
- Автозапуск, проверка обновлений правил — в v1.2 (сейчас: только локальные файлы правил + импорт вручную).
- Никакой телеметрии. Сбор статистики — только по явной кнопке «экспортировать статистику».

## 5. Нефункциональные требования

| Категория | Требование |
|---|---|
| Платформа | Windows 10 22H2 x64, Windows 11 x64. ARM64 — сборка v1.1. x86 — не поддерживается |
| Совместимость | Не использовать API выше `_WIN32_WINNT=0x0A00`; fallback для старых драйверов (D2D → GDI) |
| Производительность | Скан: ≤ 60 с на C: SSD, ≤ 25 % одного ядра; не более 8 потоков; throttling при idle |
| Память | ≤ 150 МБ рабочей; большие каталоги — потоковая обработка, без загрузки всех путей в память |
| Устойчивость | Ни один отказ IOCTL/устройства/файла не роняет процесс; каждая операция в try/catch с логированием |
| Безопасность | Рантайм-повышения нет; повышение — один раз при старте. Всегда UAC-манифест. Никаких shell-команд вида `cmd /c` для привилегированных операций — только WinAPI. Подпись бинарников (этап упаковки) |
| Пути | Поддержка длинных путей, пробелов, не-ASCII и кириллицы, hard links, ADS — определить поведение явно (ADS не трогаем) |
| Локализация | ru + en, RTL-ready, переводы в ресурсах, даты/числа через `GetLocaleInfoEx` |
| Доступность | Клавиатурная навигация, фокус, `UIA` для нативных контролов (см. ADR-3) |
| Тема | Светлая/тёмная по системной (`AppsUseLightTheme`), переклюваемая |
| DPI | Per-Monitor V2 (`SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`) |
| Приватность | Данные только локально; отчёт содержит серийники — пользователь может исключить их перед отправкой |

## 6. Архитектура

### 6.1 Слои (гексагональная архитектура)

```
┌───────────────────────────────────────────────┐
│  UI  (Win32 + Direct2D/DirectWrite)           │  единственный поток с сообщениями,
│  AppShell • DisksView • CleanupView • Report  │  рендер и ввод; без блокировок и I/O
├───────────────────────────────────────────────┤
│  Engine                                     │  оркестрация: ScanCoordinator,
│  ScanCoordinator • PlanBuilder • Executor    │  PlanBuilder, CleanupExecutor,
│  TransactionJournal • UndoService            │  Cancellation, progress
├───────────────┬───────────────────────────────┤
│  Scanner      │  Core (без Windows и без UI)  │  правила, glob, скоринг,
│  CategoryProviders (temp, browsers, wu, …)   │  модель, JSON, логирование
├───────────────┴───────────────────────────────┤
│  Platform  (Win32 обёртки)                   │  devices, ioctl, wmi, paths,
│  DiskInventory • SmartProvider • Vfs • Reg    │  privileges, restartmanager
└───────────────────────────────────────────────┘
```

**Ключевое правило:** `Core` и `Scanner` собираются и тестируются на любой платформе (в том числе на WSL-хосте) — вся Windows-специфика живёт в `Platform`. Это делает юнит-тесты быстрыми и переносимыми.

### 6.2 Модули и их ответственность

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `core::model` | Структуры данных (см. 6.3), инварианты, сериализация | — |
| `core::rules` | Загрузка/валидация правил, разбор локаторов, glob-матчинг, min-age, excludes | `core::model` |
| `core::scoring` | `ConfidenceScore`, `SafetyLevel`, ранжирование, группировка | `core::model` |
| `core::json` | Минимальный JSON writer/reader (без сторонних библиотек) | — |
| `core::units` | Форматирование размеров/процентов, склонения RU/EN | — |
| `core::log` | Структурный лог в файл + кольцевой буфер для UI | — |
| `platform::devices` | Перечисление дисков/разделов/томов, SMART-провайдер (заглушка в MVP) | Win32 |
| `platform::wmi` | COM/IWbemServices: WMI-подробности, BitLocker, storage fault | Win32 |
| `platform::vfs` | Обход каталогов, размеры, long path, reparse, удаление, корзина | Win32 |
| `platform::procs` | Restart Manager, список процессов, «кто держит файл» | Win32 |
| `platform::sysinfo` | Версия ОС, DPI, тема, локаль, привилегии | Win32 |
| `platform::net` | HTTP-загрузка набора правил (WinHTTP), TLS, таймауты, только GET | Win32 |
| `scanner::*` | Провайдеры категорий: каждый возвращает кандидатов по правилам | `core`, `platform` |
| `engine::*` | Оркестрация, план, исполнение, транзакции, undo | всё выше |
| `ui::*` | Окна, вкладки, рендер, темы, локализация, навигация | `engine`, `core` |
| `rulesync` | Загрузка/проверка набора правил: HTTP (WinHTTP), манифест, хеш, откат, офлайн-режим | `core`, `platform::net` |
| `cli` | `mrproper-cli scan --json`, `--plan`, `--apply` — headless-режим для CI и e2e | `engine` |
| `service` | Windows-сервис и планировщик (v1.2) | `engine` |

### 6.3 Модель данных

```cpp
enum class BusType { Unknown, Sata, Nvme, Usb, Scsi, Sd, Sas, Virtual, Raid };
enum class SafetyLevel { Safe, Review, Risky };
enum class PartitionKind { BasicData, System, Msr, Recovery, Oem, Efi, Reserved, Unallocated, Unknown };
enum class PlanAction { Delete, Trash, Keep, SkipLocked };

struct PhysicalDisk {
    int         number;            // 0,1,2…
    std::wstring devicePath;       // \\?\X#&…
    std::wstring model, serial, firmware;
    BusType     bus{ BusType::Unknown };
    uint64_t    sizeBytes{};
    bool        removable{}, readOnly{}, trimSupported{}, smartAvailable{};
    std::vector<Partition> partitions;
};

struct Partition {
    uint32_t index{}; uint64_t offsetBytes{}, lengthBytes{};
    std::optional<GUID> gptType; std::wstring gptName;
    uint8_t mbrType{}; bool system{}, boot{}, hidden{};
    PartitionKind kind{ PartitionKind::Unknown };
    std::optional<Volume> volume;          // если на раздел навешен том
};

struct Volume {
    std::wstring volumeGuidPath, label; std::wstring fileSystem;
    uint64_t totalBytes{}, freeBytes{};
    bool encrypted{}, dirty{}, readOnly{};
    std::vector<std::wstring> mountPoints;   // C:\ и точки-папки
    std::vector<std::pair<int, uint64_t>> diskExtents; // диск + смещение
};

struct CleanupCandidate {
    RuleId rule; CategoryId category; std::wstring path; std::wstring displayName;
    uint64_t logicalBytes{}, allocatedBytes{}; uint32_t fileCount{};
    FILETIME oldestWrite{}, newestWrite{}, lastAccess{};
    SafetyLevel safety{ SafetyLevel::Review }; int confidence{};
    std::vector<std::wstring> reasons; std::vector<ProcessRef> lockedBy;
};

struct CleanupPlanItem { CleanupCandidate candidate; PlanAction action; uint64_t reclaimBytes; };
struct ScanResult { std::vector<PhysicalDisk> disks; std::vector<CleanupCandidate> candidates; ScanStats stats; };
```

Инварианты (проверяются в тестах): `allocatedBytes ≤ logicalBytes` (с оговоркой на sparse/сжатие — тест на fixture), `reclaimBytes` равно `allocatedBytes` для `Delete`/`Trash`, `confidence ∈ [0,100]`, путь кандидата находится внутри корня правила.

### 6.4 Потоки и отмена

- Один UI-поток (владеет HWND и D2D-ресурсами).
- Пул рабочих потоков для IOCTL-обхода и файлового IO; счётчик файлов/байт публикуется атомарно, UI читает раз в 100 мс.
- `CancellationToken` = `std::stop_source` (C++20) + `std::stop_token` в IO-циклах; отмена кооперативная, проверка каждые 256 элементов.
- Результаты не мутируются после публикации: `shared_ptr<const ScanResult>`.

## 7. Интерфейс: Direct2D + нативные контролы (ADR-3)

**Решение.** Таблицы (список дисков, дерево очистки) рисуются **нативными контролами с кастомной отрисовкой** (`SysListView32` + `NM_CUSTOMDRAW`, `SysTreeView32`), а **Direct2D** используется для графики собственной природы: карта разделов (вложенные полосы), кольцевые/линейные диаграммы, анимация прогресса, health-виджеты (v1.1).

**Почему.** Полностью кастомный Direct2D-рендер всего UI означает: ручную реализацию скролла, выделения, клавиатурной навигации, адаптивной вёрстки, экранного диктора и UI Automation (стоимость ×3–5 к бюджету MVP). Гибрид оставляет 90 % преимуществ (своя графика там, где это ценно) при доступности «из коробки».

Следствия: `Direct2D` нужен для `DisksView` с первого дня; таблицы — на `NM_CUSTOMDRAW`; тема и DPI — общие для обоих путей.

### 7.1 Основные экраны

1. **Обзор** — дашборд: карта дисков, крупные кандидаты очистки, быстрые действия.
2. **Диски** — дерево дисков/разделов/томов + карточка деталей + «Экспорт карты».
3. **Очистка** — дерево категорий, чекбоксы, агрегаты, dry-run, «Очистить сейчас».
4. **Отчёт** — результат последней операции + журнал + экспорт.
5. **Настройки** — правила, безопасность, автозапуск, о программе.

### 7.2 Гайдлайн по UX (минимум)

- Ничего не удаляется без явного действия и списка того, что будет удалено.
- Для каждого элемента: объём, возраст, объяснение, иконка риска.
- Оценка освобождаемого места — большая цифра сверху, всегда с указанием «по аллоцированному размеру».
- Отмена (Ctrl+Z) доступна, пока транзакция не «схлопнулась» (то есть пока корзина не переполнена).

## 8. План работ (этапы)

Каждый этап имеет проверочную команду — «машинно проверяемый результат», а не «посмотрели глазами» (принцип: результат этапа должен воспроизводиться в CI).

### Этап 0.0 — Тулчейн (0.5–1 день, обязательная предусловия)

На машине владельца C++-тулчейна нет: VS 2022 Community стоит **без C++ workload**, единственный компилятор — MSVC 14.29 (v142) из VS 2019 Build Tools, в нём нет `std::stop_token`/`std::jthread`; CMake и vcpkg отсутствуют.

- Установить **Visual Studio Build Tools 2022** (рабочая нагрузка «Разработка классических приложений на C++»: MSVC v143, Windows 11 SDK 10.0.22621+), **CMake** ≥ 3.28, **vcpkg**, `clang-format`/`clang-tidy`.
- Проверить, что доступны `std::stop_source`/`std::jthread`, `std::filesystem`, `<format>`; если нет — либо доплатить toolset, либо заменить `std::stop_token` собственной обёрткой (решение принимается на старте Этапа 0, ADR-001).
  - **Уточнение по факту (задача 01, реальный прогон на этой машине):** MSVC 14.29 (v142) из VS 2019 Build Tools **имеет** `std::stop_token`/`std::jthread`, `std::format`, `std::filesystem` и `std::ranges`. Собственная обёртка отмены не нужна, движок может опираться на `std::stop_source` (SPEC §6.4). Ограничение v142 другое и реальное: **ASan-рантайм не инициализируется** (0xC0000142) даже с копией DLL рядом с exe, поэтому санитайзеры включаются только на VS 2022 и на GCC/Clang, а пресет `dev` на этой машине собирается без них.
- **Проверка:** `cmake --version`, `cl` в «Developer Command Prompt» печатает версию v143, `vcpkg list` работает, тривиальный проект собирается и запускается.
- В CI (GitHub Actions `windows-latest`) VS 2022 с C++ и CMake уже есть — локальная установция нужна только владельцу.

### 9.1 ADR-заготовки (решения, которые фиксируем сразу)

- **ADR-001 Стек: C++20 + Win32 + Direct2D.** Единственный нативный доступ к дискам без рантайма; минус — скорость разработки и риск ошибок в unsafe-коде. Митигация: `-W4 -WX`, sanitizers, изоляция WinAPI в `platform/`, Rust-подобные обёртки (RAII для HANDLE, `unique_handle`).
- **ADR-002 Правила очистки — данные (JSON), не код.** Обновления безопасности без перевыпуска; но требует валидации и версионирования схемы.
- **ADR-003 Гибрид Direct2D + нативные контролы** (см. §7).
- **ADR-004 Core без Windows-зависимостей** — ради тестируемости на хостовой машине и переносимости правил/скоринга.
- **ADR-005 Своя корзина вместо системной** — системная корзина не масштабируется на десятки ГБ кэшей и не даёт транзакции; минус — занимает место, пока не очищена.
- **ADR-006 Удаление кэшей напрямую, не через корзину ОС** — `IFileOperation` с `FOF_ALLOWUNDO` на больших объёмах упирается в лимиты и заметно медленнее.
- **ADR-007 Никакой телеметрии, отчёт — единственный канал наружу** (приватность + доверие к утилите, которая удаляет файлы).
- **ADR-008 Правила обновляются с GitHub, но никогда не применяются без проверки.** Поскольку правила управляют удалением файлов, подменённый набор правил — это вектор удаления данных. Поэтому: набор подписывается Ed25519-ключом, приватная часть которого хранится офлайн у владельца и никогда не попадает в репозиторий; публичная часть встроена в бинарник; скачивание идёт по HTTPS с пином тега; при несовпадении подписи/схемы/хеша — откат на последний рабочий набор в `%LOCALAPPDATA%\MrProper\rules\`. Альтернатива (только ручной импорт) отклонена: правила устаревают быстрее, чем выходят релизы.
- **ADR-009 Сборки не подписываются.** Утилита личная, сертификата нет; цена — предупреждение SmartScreen и «неизвестный издатель». Смягчение: инструкция в README, portable-сборка в ZIP, публичные хеши сборок в релизных заметках.
### 9.2 Обновление правил с Git (v1.0, ADR-008)

Правила управляют тем, что приложение удаляет, поэтому канал обновления проектируется как недоверенный вход.

**Формат набора**

```
rules/                       # в репозитории, версионируется
  manifest.json              # { "schema": 1, "version": "2026.02.1",
                           #   "files": [{"path":"temp.user.json","sha256":"…","size":1234}],
                           #   "minAppVersion": "1.0.0" }
  <категория>.json           # сами правила
rules.sig                    # Ed25519-подпись манифеста (base64)
```

**Поток обновления**

1. При запуске (не чаще раза в 24 ч) `rulesync` спрашивает у заданного URL (тег `rules/vX.Y` в репозитории) `manifest.json` + `rules.sig`; запрос только `GET` по HTTPS, таймаут 10 с, без куки и авторизации.
2. Проверка: схема манифеста, `minAppVersion` ≤ текущей версии, подпись Ed25520 публичным ключом, встроенным в бинарник, затем SHA-256 каждого файла.
3. Только после этого файлы скачиваются в staging-каталог рядом с целевым, валидируются парсером (неизвестные поля — ошибка, битый JSON — ошибка) и атомарно подменяют рабочий набор.
4. Любая ошибка на шагах 1–3 → тихий отказ с записью в лог, приложение продолжает работу на предыдущем рабочем наборе. Приложение никогда не остаётся без набора правил.
5. Пользователь видит в настройках: текущая версия набора, дата, результат последней проверки, кнопки «проверить сейчас» и «вернуть встроенный набор».

**Офлайн-режим и сброс**

- Приложение полностью работоспособно без сети: используется последний проверенный набор либо встроенный в бинарник.
- «Вернуть встроенный набор» — обязательная кнопка: удаляет скачанные правила, оставляя встроенные, и отключает автообновление до следующего явного включения.

**Управление ключом (владелец, офлайн)**

- Приватный Ed25519-ключ генерируется один раз локально, хранится **вне репозитория** (зашифрованный файл в личном хранилище), используется только для подписи наборов правил.
- Публичный ключ попадает в исходники как константа (`core::rules::kRuleSetPublicKey`) и ревьюится как обычный код.
- Подписание набора — скриптом `tools/sign-rules.ps1`, запускаемым вручную или в отдельном workflow с self-hosted раннером (секрет в репозитории не хранится).

**Почему не «просто скачать JSON»**

Одно неверное правило — это удаление пользовательских данных. Пин тега + подпись + атомарная подмена + откат стоят ~2 дней работы и превращают риск из «тихо удалит» в «не применится и напишет в лог».

- **ADR-010 Репозиторий публичный, лицензия MIT.** Следствия: обязательные `SECURITY.md` (как сообщать об уязвимости и почему нельзя прикладывать отчёты с серийниками), `CONTRIBUTING.md`, шаблоны issues, CI на публичных раннерах.

## 11. Стратегия тестирования

0. **CI (GitHub Actions, `windows-latest`)** — образ уже содержит VS 2022 с C++ workload и CMake, поэтому тулчейн владельца для CI не нужен. Матрица: Debug/ASan+UBSan, Release; шаги `configure → build → ctest → clang-tidy`.
1. **Юнит-тесты (Core, без Windows)** — правила, glob, min-age, скоринг, JSON, форматирование, инварианты модели. Запускаются в CI на каждом PR за секунды.
2. **Интеграционные (Windows)** — обёртки WinAPI против реальных путей: создать структуру каталогов → просканировать → сверить с суммой `GetCompressedFileSize`; sparse-файлы; длинные пути; reparse-петля; заблокированный файл.
3. **E2E на VM-образах (Pester/PowerShell)** — 20 сценариев: полный цикл, частичная очистка, отмена, восстановление, приложение держит файл, зашифрованный том, диск с битыми секторами в эмуляции, отсутствие прав, первый запуск, обновление правил.
4. **Golden-тесты данных** — JSON-дампы карты дисков и плана; расхождение = падение CI (с исключениями по нестабильным полям вроде свободного места).
5. **Фаззинг правил** — случайные/битые JSON-правила не должны ронять приложение (property-based тесты).
6. **Нагрузочные** — каталог 500 тыс. файлов: время, память, отзывчивость UI, корректная отмена.

## 12. Критерии приёмки MVP (Definition of Done)

MVP считается готовым, когда одновременно:

- [ ] На 3 эталонных VM (MBR/BIOS, GPT/UEFI, мультидиск) карта разделов совпадает с эталоном: 100 % дисков, разделов и томов, 0 расхождений по суммам размеров.
- [ ] Скан на C: SSD занимает ≤ 60 с и ≤ 25 % одного ядра; отмена работает мгновенно.
- [ ] Все 20 e2e-сценариев зелёные, включая восстановление 100 % удалённого и отсутствие изменений вне корней правил.
- [ ] Ни один элемент не удаляется без видимого объяснения и уровня риска; `Risky` по умолчанию скрыты.
- [ ] Отчёт (HTML/JSON) содержит карту, кандидатов, операции и ошибки; открывается без приложения.
- [ ] Приложение запускается без повышения прав; повышение запрашивается только на операции.
- [ ] 0 крашей и 0 необработанных исключений на сценариях 2–6; все ошибки в логе с путём и HRESULT.
- [ ] `clang-tidy` чист, `/W4 /WX` без предупреждений, санитайзеры (ASan/UBSan) в debug-режиме зелёные на e2e.
- [ ] Русская и английская локализация полны, нет обрезанных строк при 150 % DPI.
- [ ] Установка/удаление через установщик проходят на чистой VM, лог установки без ошибок.
- [ ] Обновление правил с GitHub работает: подписанный набор применяется, неподписанный/битый откатывается с записью в лог, работает офлайн-режим.
- [ ] В репозитории есть `LICENSE` (MIT), `SECURITY.md`, `CONTRIBUTING.md`, шаблоны issues; в README описаны неподписанность сборки и ожидаемое предупреждение SmartScreen.

## 13. Принятые решения и остаток открытых вопросов

### 13.1 Решения владельца (закрывают открытые вопросы)

| Вопрос | Решение | Последствия для спеки |
|---|---|---|
| Имя продукта | **MrProper** | Строки версии, каталоги `%LOCALAPPDATA%\MrProper`, `%ProgramData%\MrProper`, имя сервиса, протокол `mrproper:`. Риск совпадения с торговой маркой вынесен в §10, решение — оставить |
| Здоровье носителей | **v1.1** (не в MVP) | В MVP только TRIM/кэш записи в карточке диска; интерфейс `IHealthProvider` закладывается в v1.0, реализация — v1.1 (Этап 6) |
| Репозиторий | **Публичный** | MIT, `SECURITY.md`, `CONTRIBUTING.md`, шаблоны issues, CI на `windows-latest`, Dependabot/Renovate (ADR-010) |
| Подпись кода | **Не нужна** (личное использование) | Сборки unsigned, SmartScreen-предупреждение документировано, вместо подписи — публичные SHA-256 в релизных заметках (ADR-009) |
| Целевой пользователь | **Домашний ПК владельца** | Приоритет: безопасность → объяснения → обратимость → скорость. CLI только для разработки; GPO/корпоративные функции исключены (§1.1) |
| Обновление правил | **С Git** (решено: можно) | Модуль `rulesync` в v1.0 (Этап 5) + подпись Ed25564, пин тега, проверка целостности, автоматический откат (ADR-008, §9.2) |
| BitLocker | **Достаточно определения факта шифрования** | Работа с VSS/ теневыми копиями исключена из области; определение — WMI `Win32_EncryptVolume`, поле в карточке тома |
| Стек | **C++ / Win32 + Direct2D, с нуля** | DiskInsight (`/mnt/d/Project/DiskInsight`) не переиспользуется; используется только как источник идей и фикстур. Тулчейн ставится отдельной задачей (Этап 0.0) |

### 13.2 Что осталось открытым (решать по ходу, не блокирует старт)

1. **Версия Windows как минимум.** Спека ориентируется на Windows 10 22H2; решение «поддерживаем только 11» упростит код (нет fallback-п веток) и снимет часть §5.
2. **Куда указывает `rulesync`:** raw-файлы по тегу `rules/vN` или release-архив. Для личного проекта разницы почти нет; влияет только на скрипт CI-подписи.
3. **Что делать с `/mnt/d/Project/DiskInsight`:** оставить как есть, вынести в архив или удалить. На спеку не влияет, но ~3 ГБ (логи сборок и `.rar`) в `D:` не нужны — там свободно 65 ГБ.
4. **Оценка «умности» скоринга.** До первых замеров на своём ПК нельзя честно обещать число кандидатов; G2 уточняется после Этапа 2.
