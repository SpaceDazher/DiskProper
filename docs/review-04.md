## 3. Находки

### F-01. Второй `start()` у исполнителя очистки убивает процесс

**Вердикт: ДЕФЕКТ, ПОДТВЕРЖДЁН ЧТЕНИЕМ. Влияние: критическое (падение процесса).**

Где: `src/engine/executor.cpp:1601` (`runner_ = std::jthread(...)`), `:1657-1666`
(`wait()` и `waitFor()` не присоединяют поток), `:1727-1732` (присоединяет только
деструктор), `:1423-1448` (`beginRun`).

Суть. `runner_` — `std::jthread`. Он переиспользуемый: прогон завершается, и
`finalize()` снимает признак занятости (`running_ = false`, `executor.cpp:1257-1261`),
но **поток не присоединяется**: `wait()` и `waitFor()` только ждут условия
(`doneCv_.wait(lock, [this] { return !running_; })`), а `join()` есть только в
деструкторе. Присваивание в joinable-поток — `std::terminate()` (требование
предусловия `!joinable()`; в MSVC это `_VALIDATE_ASSUME`, он активен и в Release).

Сценарий, полностью укладывающийся в заявленный контракт класса («уже идёт прогон →
`AlreadyRunning`, повторный клик «Очистить» игнорируется», `executor.hpp:350` и
`:485-486`; и «`start()` … можно звать из UI- и рабочих потоков», `executor.hpp:456-458`):

1. `start()` — фоновый `jthread` #1 отработал фазы A–D, отчёт опубликован;
2. пользователь нажимает «Очистить» ещё раз (это ровно то, ради чего класс и писался:
   `generation_` растёт, `result_` сбрасывается, `stop_` пересоздаётся);
3. `beginRun()` видит `running_ == false` и разрешает прогон;
4. `runner_ = std::jthread(...)` — прежний поток ещё joinable → процесс падает.

Почему это не поймано: единственное сегодня production-потребление — `run()`
(`cmd_apply.cpp:592` прямо пишет, что исполнитель ещё не подключён), а `run()`
потока вообще не создаёт, поэтому `runner_` остаётся не-joinable и деструктор
срабатывает один раз. В UI путь `start()` — единственный, и он как раз ломается.

Чинить надо в `executor.cpp` (владелец — слой engine, не этот документ): привести
`start()` к уже написанному в координаторе образцу — `src/engine/scan_coordinator.cpp:503-514`:
вынести прежний `runner_` под мьютексом, отпустить мьютекс, присоединиться, снова
взять мьютекс и перепроверить `running_`. Второй, независимый вариант — присоединять
поток в `finalize()`/после `running_ = false`, но это меняет смысл `result()`
(отчёт опубликован, а поток ещё жив) и требует явного решения, где именно ждать.

### F-02. `waitForIdle()` ждёт сигнала, которого не бывает

**Вердикт: ДЕФЕКТ, ПОДТВЕРЖДЁН ЧТЕНИЕМ. Влияние: среднее (функция не работает).**

Где: `src/platform/inventory.cpp:1191-1194` (`waitForIdle`), `:1253` (`busy_ = false`),
`:1153` (`requestRefresh` → `wake_.notify_one()`), `:1091` (деструктор → `notify_all`).
Проверено `grep`: других `notify_*` в файле нет.

Суть. `waitForIdle` ждёт на `wake_` предикат `!pending_ && !busy_`. `busy_`
снимается в `runCollection` на `:1253` — и **сигнала там нет**: `wake_` будится
только в `requestRefresh` (`:1153`) и в деструкторе (`:1091`). Обход дисков
заканчивается тихо.

Следствие: `waitForIdle(timeout)` возвращает `false` по таймауту всегда, кроме
случая, когда кто-то успел заказать следующий проход. Обещание API («дождаться
простоя») не выполняется, и вызывающий получает ложный «обход не успел».

Почему это не поймано: `waitForIdle`, `refreshNow` и `requestRefresh` сегодня не
вызываются **нигде вне `inventory.cpp`** (проверено `grep` по `src/` и `tests/`):
кэш инвентаризации написан, но ещё не подключён к приложению. То есть находка
латентная по построению, а не по недосмотру теста.

Чинить: `notify_all()` сразу после `busy_ = false` (и после `pending_ = false` в
`requestRefresh` — там `notify_one` достаточно, потому что ждёт только поток обхода).

### F-03. Синхронный `refreshNow()` — это минуты блокировки в вызывающем потоке

**Вердикт: ДЕФЕКТ, ЛАТЕНТНЫЙ. Влияние: среднее-высокое (заморозка окна, §6.1).**

Где: `src/platform/inventory.cpp:1125-1127` (`refreshNow` → `runCollection`),
`:1237-1240` (`collectionMutex_` на весь обход).

Суть. Обход устроен правильно — один за раз, «мьютекс не тот, что у состояния:
первый можно держать минуты» (комментарий автора). Но `refreshNow()` — публичный
API, который зовёт `runCollection` **в потоке вызывающего**. Если этим API
воспользуется UI-поток (а он воспользуется: карту дисков надо обновить при
`WM_DEVICECHANGE` до следующей отрисовки), он встанет на `collectionMutex_` на всё
время обхода. Спека требует обратного: §6.1 «UI — без блокировок и I/O», §6.4
«Один UI-поток» — то есть UI не имеет права ждать завершения дискового обхода.

Разница с `requestRefresh()` в этом — принципиальная: `requestRefresh` только ставит
флаг и будит уже существующий поток (`ensureWorkerLocked`, `:1120-1123`) и
возвращается сразу. То есть в модуле уже есть правильный способ, а неправильный
экспортирован рядом с ним и ничем не помечен.

Чинить: убрать `refreshNow()` из публичного API либо переименовать в
`collectNow()` и объявить в шапке, что звать только из фонового потока и не из
UI; для UI оставить единственный путь `requestRefresh()`.

### F-04. Отрисовка журнала ждёт глобальный мьютекс, который держат через файловую запись

**Вердикт: ДЕФЕКТ, ПОДТВЕРЖДЁН ЧТЕНИЕМ. Влияние: среднее (подвисание UI при скане).**

Где: писатель — `src/core/log.cpp:418-440` (`Logger::write` берёт `mutex_` и держит
его до конца, включая вызов `appendLineLocked` на строке 439), `:447-461`
(`appendLineLocked` → `fwrite` на 452 + `fflush` на 460 **под тем же мьютексом**,
«сбрасываем на диск после каждой записи»); читатель из UI —
`src/ui/view_report.cpp:972-985` (`refreshJournal` → `Logger::snapshot`),
`:2174` + `:2380-2383` (таймер `kTimerJournal` раз в 500 мс зовёт `refreshJournal`,
когда счётчик записей изменился), снимок — `src/core/log.cpp:463-474`.

Суть. Один мьютекс на весь процесс покрывает и сборку записи (строки, `clip`,
форматирование), и **дисковую запись с принудительным сбросом на файл**. Пока идёт
скан, фоновые потоки пишут записи (прогресс, отказы по элементам), и каждый такой
`write` держит `mutex_` на время `fflush`. UI-поток экрана «Отчёт» в этот же
момент берёт **тот же** мьютекс в `Logger::snapshot()` и копирует кольцо
(ёмкость 512 записей, `log.hpp:100`).

То есть §6.1 «UI — без блокировок» нарушено не абстрактно, а на конкретном пути:
таймер экрана «Отчёт» стоит в очереди за файловой записью фонового потока. Время
ожидания — длина `fflush` на текущем носителе плюс время, пока держит мьютекс любой
другой писатель; при 16 рабочих потоках это очередь, а не одна запись.

Оговорка, чтобы не переоценить: `Logger::lastSequence()` атомик и мьютекса не берёт
(`log.cpp:482-484`) — то есть дешёвая проверка «есть новое» безопасна, дорогая
`snapshot()` в полосе не вызывается зря.

Чинить (core — чужой слой, здесь только вывод): развести два мьютекса — кольцо под
своим, файл под своим; либо вынести файловую запись в отдельную очередь с одним
писателем. Снимок кольца тогда берёт только свой мьютекс, и путь отрисовки
перестаёт зависеть от диска.

### F-05. `tr()` берёт мьютекс каталога в пути отрисовки, и комментарий утверждает обратное

**Вердикт: ДЕФЕКТ, ПОДТВЕРЖДЁН ЧТЕНИЕМ. Влияние: низкое (сейчас), правило §6.1 нарушено.**

Где: читатель — `src/core/i18n.cpp:423-425` (`Localizer::tr` → `catalog()`), `:361-364`
(`Localizer::catalog()` берёт `catalogMutex_`); писатель — `:344-357`
(`Localizer::mutate` **под тем же мьютексом копирует весь `StringCatalog`**).

Путь в UI: `view_cleanup.cpp:2092-2110` (`drawSummary` зовёт `summaryText()`,
`selectedText()`, `safeOnlyText()`, `lockedText()`, `reclaimHintText()` и
`trPlural`) — это обработчик `WM_DRAWITEM` (`:2286`), то есть чистая отрисовка; плюс
те же вызовы в подписях строк при `NM_CUSTOMDRAW`.

Почему это дефект, а не стиль: комментарий в `mutate` (`:345-347`) утверждает
«читатели держат свой снимок каталога и **не блокируются**». Это неверно — `tr()`
берёт `catalogMutex_` на каждый вызов. Инвариант «в модели экрана блокировок нет»
(`view_report.hpp:85-87`, `view_cleanup.hpp:62-63`) тем самым нарушен неочевидным
способом: не в классе экрана, а через глобальный локализатор.

Оценка severity низкая и обоснована: единственный production-писатель под этим
мьютексом — `loadCatalog` (`i18n.cpp:376-382`), который под мьютексом меняет только
указатель; `mutate` с копированием каталога в приложении не вызывается вовсе
(проверено `grep`: `addString`/`setString` не имеют вызывающих в `src/`). То есть
сейчас блокировка берётся, но почти никогда не ждёт. Дефект в инварианте и в
документации, а не в текущей задержке кадра.

Чинить: `catalog()` сделать безблокировочным (атомарный `shared_ptr` — в MSVC v142
это `std::atomic_load/atomic_store` по свободной функции, без `std::atomic<shared_ptr>`),
либо честно переписать комментарий и правило слоя: «UI берёт мьютекс каталога, он
не contended».

### F-06. Отмена и старт нового прогона делят один `stop_source` без общего замка

**Вердикт: ДЕФЕКТ, ЛАТЕНТНЫЙ. Влияние: среднее (гонка, по контракту класса).**

Где: `src/engine/executor.cpp:1670-1675` (`requestStop` — без мьютекса),
`:1423-1448` (`beginRun` — `stop_ = std::stop_source{}` под `mutex_` на строке 1442).

Суть. Заявленный контракт класса (`executor.hpp:470-472`): «`start()`, `run()`,
`requestStop()`, `progress()`, `result()`, `running()` можно звать из UI- и рабочих
потоков одновременно». Для `start()`/`requestStop()` это неправда: `requestStop()`
делает `stop_.request_stop()` без `mutex_`, а `beginRun()` в этот же момент под
`mutex_` присваивает `stop_` новый источник. Присваивание `std::stop_source` и
`request_stop()` на одном объекте из двух потоков — гонка.

Доказать, что в текущем приложении это не стреляет, легко: единственный будущий
вызывающий — UI-кнопка «Отмена», то есть тот же поток, что и «Очистить». Но
контракт в заголовке разрешает другое, а защита, которая в соседнем классе уже
написана и работает (`scan_coordinator.cpp:570-575`, с комментарием «мьютекс
обязателен … без мьютекса это была бы гонка "отменяем уже чужой прогон"»), здесь
потеряна.

Чинить: взять `mutex_` в `requestStop()` до `request_stop()`; `notify_all()` по
`doneCv_` оставить после снятия мьютекса, если так дешевле (он не блокирует).

### F-07. Мост модель↔представление не защищён от разрушения во время публикации

**Вердикт: РИСК, ЛАТЕНТНЫЙ. Влияние: высокое, но потребителя пока нет.**

Где: `src/ui/mv_bridge.hpp:380-390` (жизненный цикл, пункт 4), `mv_bridge.cpp:562-576`
(деструктор), `:678-755` (`postEvent` из любого потока), `:758-815` (`postProgress`).

Суть. `postEvent`/`postProgress` разыменовывают `impl_`, `impl_->dispatcher`,
`impl_->slot` **без блокировки** — это и есть замысел файла («в мосте вообще нет
contended-состояния»). Защита от разрушения сделана наполовину: счётчики вынесены в
разделяемый `BridgeCounters` с флагом `alive`, и уже поставленная работа проверяет
`alive` перед разыменованием `owner` (`:713`) — то есть **уже отправленный** кадр
не приведёт к обращению к освобождённому `this`. Но сама отправка — нет: если
`postEvent` выполняется на фоновом потоке одновременно с `~ModelViewBridge`, то
`impl_->dispatcher.reset()` (`:575`) и `destroySink()` (`:574`) идут под указатель,
который в эту секунду использует отправитель.

Заголовок это прямо признаёт: «Публиковать в разрушенный или разрушаемый мост
нельзя, и мост не берёт на себя проверку этого» (`mv_bridge.hpp:385-388`). То есть
контракт «фоны остановлены и присоединены до разрушения моста» — требование к
владельцу, и его пока некому выполнить: `app_shell.cpp` моста не создаёт, grep по
`src/` даёт единственные упоминания в комментариях `nav.hpp:300`,
`view_cleanup.hpp:53`, `view_disks.hpp:55`.

Чинить (не в этом документе): в `app_shell` завести явный порядок разрушения —
сначала `CleanupExecutor`/`ScanCoordinator`/`InventoryCache` (деструкторы просят

### F-08. Слияние прогресса может потерять сигнал; спасает только таймер

**Вердикт: НЕОПАСНЫЙ ДЕФЕКТ. Влияние: низкое (задержка до 100 мс).**

Где: `src/ui/mv_bridge.cpp:786-812` (кладёт кадр в слот на строке 790 и берёт флаг
`progressWake.exchange(true)` на 805), `:869` (`deliverProgress` сбрасывает
`progressWake` после забора кадра).

Сценарий «потерянного пробуждения». Фон кладёт кадр в слот (`:790`) и берёт флаг.
UI в это время уже забрал предыдущий кадр, но ещё не сбросил флаг
(`deliverProgress` сбрасывает его на `:869`, после забора). Фон видит `true`,
сигнал не ставит, выходит. UI сбрасывает флаг. В слоте лежит кадр, на который никто
не посмотрит — до следующего `WM_TIMER` (страховка `:249-256` в шапке, период
`tickInterval` = 100 мс).

Оценка: это не потеря данных, а задержка, и именно ради неё в модуле и сделан
таймер-страховка (`mv_bridge.hpp:404-407`, `tickInterval`). Поэтому дефект, а не
обход: канал «сигнал» сам по себе недостаточен, и это стоит написать в шапке,
иначе следующий оптимизатор уберёт таймер как «лишний таймер, кадр и так доедет».

### F-09. Пробелы в тестовом покрытии: потоков, отмены и публикации нет вообще

### F-10. Проверенные контроли: обход не найден

Эти места проверялись отдельно, и они сделаны правильно — их не следует трогать
в ходе исправления F-01…F-08.

1. **Публикация результата атомарна и иммутабельна.** `ScanRunReport` публикуется
   как `shared_ptr<const ScanRunReport>` под `stateMutex_` вместе со снятием
   `running_` (`scan_coordinator.cpp:858-864`); читатели берут копию указателя под
   тем же мьютексом (`:589-592`). Порядок «последний снимок прогресса уходит раньше,
   чем UI увидит `running() == false`» выдержан (`progressThread.join()` на строке
   680 до `publishReport` на 682, `:679-682`).
2. **Поток прогресса не блокирует и не удерживает мьютекс состояния во время
   колбэка.** `progressLoop` отпускает `stateMutex_` до `emitProgress`
   (`scan_coordinator.cpp:724-730`) — иначе колбэк, зовущий `requestStop()`, взял бы
   тот же мьютекс, который сам же и ждёт.
3. **Колбэк копируется по значению и не держит `this`.** `scan_coordinator.cpp:758-764`
   и `executor.cpp:1389-1392`: отложенный вызов после разрушения координатора
   безопасен — это прямо следует из «копия, а не указатель».
4. **`WorkerPool::close()` — дренирование, а не отбрасывание.** Очередь дорабатывается
   до закрытия (`scan_coordinator.cpp:361-380`), `drain()` ждёт по отдельному
   `condition_variable idle_`, и уже после этого `workers_.clear()` присоединяет
   потоки. Незакрытые слоты `std::function` удаляются явно (`:433-437`).
5. **Отмена из обработчика сигнала не берёт мьютекс.** `cmd_scan.cpp:128-130`:
   обработчик `SIGINT` только взводит `volatile std::sig_atomic_t`; `requestStop()`
   зовёт поток прогресса (`:525-527`) и сторож `--timeout` (обычный поток,
   `TimeoutWatchdog`, `:539-551`). Это ровно то, что нужно делать с обработчиком
   сигнала, и единственное место, где легко было ошибиться, — сделано правильно.
6. **Таймаут на устройство не оставляет висящих указателей.** `size_probe.cpp:145-196`:
   слот состояния в `shared_ptr`, поток отсоединён и убирает состояние сам. Мёртвый
   диск стоит одного «брошенного» вызова (счётчик `gAbandonedCalls`) и не портит
   вызывающему память.
7. **Проверка отмены стоит там, где надо, и с той частотой, что в спеке.**
   `vfs_walk.cpp:319-330` — раз в `cancelCheckPeriod` элементов, значение по
   умолчанию 256 (`vfs_walk.hpp:89`), с явным объяснением, почему не на каждом
   элементе. Верхний уровень сбора проверяет токен на границе правила
   (`candidate_collector.cpp:656-659`).
8. **Экран «Отчёт» не держит указатели на журнал.** `JournalRow`
   (`view_report.hpp:157-196`) — глубокие копии строк; комментарий прямо называет
   причину (событие приезжает позже отчёта). Проверено: `rows()` не отдаёт
   `core::LogRecord*`.
9. **UI не блокируется на своих собственных полях.** В `src/ui` нет ни `std::mutex`,
   ни `std::thread`, ни ожиданий (проверено `grep`): единственные атомики — в
   `locale.cpp` (инициализация, ревизия, направление текста), и они не ждут.
   Плюс `kMsgSyncModel` (`view_cleanup.cpp:1327`, `view_disks.cpp:1453`,
   `view_report.cpp:1676`, `view_settings.cpp:1223`) — перерисовка отложена
   `PostMessage`, чтобы не перестраивать дерево внутри его же `TVN`.
10. **Деструкторы не бросают наружу и присоединяют потоки.**
    `~ScanCoordinator` (`:483-486`), `~CleanupExecutor` (`executor.cpp:1727-1732`),
    `~InventoryCache` (`inventory.cpp:1086-1093`) — во всех трёх остановка
    запрашивается до присоединения; в `InventoryCache` дополнительно проверяется
    `stopping_` перед публикацией снимка (`:1255`).

## 5. Как проверялось

Ревью статическое по коду. Сборка и тесты слота `a94` — зелёные, чужих файлов не
трогал (в этом документе нет ни одной правки кода):

```
cmd.exe /c "tools\build.bat Debug a94"   → [build] ok: build\a94
cmd.exe /c "tools\test.bat Debug a94"    → ALL PASS: 305 проверок, провалов 0
```

Что проверено прогоном, а что только чтением (честная граница):

* **Прогоном (реальный параллельный скан с отменой).** `mrproper_cli scan` в слоте
  `a94` прогоняется через `ScanCoordinator::run()` с пулом потоков — это единственное
  production-потребление §6.4. Отмена проверена существующим `--timeout` и Ctrl+C:
  оба доходят до `requestStop()` из потока, не из обработчика сигнала (F-10.5), и
  отчёт помечается `cancelled`, а незакрытые задачи становятся `Cancelled`, а не
  молча пропадают (`scan_coordinator.cpp:823-831`). Это единственная часть §6.4,
  которая сегодня исполняется настоящим кодом с настоящими потоками.
* **Только чтением (подтверждено построчно, но не исполнено).** F-01, F-02, F-03,
  F-05, F-06, F-07, F-08. Причина одна и общая: у них нет ни одного потребителя.
  `CleanupExecutor` — CLI прямо пишет «исполнитель операций ещё не подключён»
  (`cmd_apply.cpp:592`), UI его не зовёт; `InventoryCache` не вызывается вне своего
  файла; `ModelViewBridge` не создан в `app_shell`. Написать «прогон показал» про
  них было бы неправдой, поэтому они помечены как подтверждённые чтением кода, а не
  исполнением.
* **Чего проверить нельзя было в принципе.** Поведение UI под нагрузкой (реальная
  отрисовка, реальные 16 потоков скана на живом томе) требует запущенного окна;
  тестового стенда с GUI в проекте нет, а e2e-сценарии (`tests/e2e/*.ps1`) —
  консольные. Для F-04 и F-05 это осознанное ограничение: вывод сделан по коду
  (замок в пути отрисовки, писатель под ним с файловым вводом-выводом) и по
  документации самого кода, которая утверждает обратное.

## 6. Приложение: карта потоков и того, что они делят

|---|---|---|---|
