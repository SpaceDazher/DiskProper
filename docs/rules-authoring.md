# Авторство правил очистки

Документ отвечает на два вопроса:

1. **Как добавить категорию или правило очистки** — пошаговая процедура и точный формат файла.
2. **Что можно чистить безопасно** — почему конкретные категории получили уровень `safe`,
   а другие не могут его получить в принципе.

Правила очистки — **данные, а не код** (ADR-002): они поставляются с приложением и обновляются
без пересборки. Но именно они решают, какие файлы будут удалены, поэтому к ним применяется
планка на уровне правил удаления из пользовательских данных (ADR-008, SPEC §10).

Источники истины, в порядке убывания авторитетности:

| Что | Где |
|---|---|
| Разбор и валидация полей (список допустимых имён, типы, проверки) | `src/core/rules.cpp` |
| Структуры `Rule` / `RuleSet` | `src/core/rules.hpp` |
| Синтаксис шаблонов путей | `src/core/glob.hpp`, `src/core/glob.cpp` |
| Требования к поведению (оценка кандидатов, план, удаление) | `docs/SPEC.md` §4 FR-3…FR-6 |
| Каталог категорий и требуемые уровни риска | `docs/SPEC.md` §4 FR-3 |
| Формат набора, манифест, подпись, обновление | `docs/SPEC.md` §9.2, ADR-008 |

Если этот документ расходится с `src/core/rules.cpp` — правьте документ, а не код:
загрузчик правил и документация обязаны описывать одно и то же поле.

## 1. Что где лежит

```
rules/
  manifest.json        # версия и хеши набора; подписывается (ADR-008)
  <категория>.json     # один файл — одна категория, внутри массив rules
rules.sig              # подпись Ed25519 манифеста (base64), появляется при релизе набора
```

Правило: **один файл — одна категория**. Имя файла совпадает с `category` правил внутри
(`browser.cache.edge.json` содержит правила с `"category": "browser.cache"`). Файл может
содержать несколько правил — по одному на вариант (браузер, каталог, профиль-группа).

Набор правил целиком (все файлы из каталога) — это `rules/`; он версионируется в git,
и его версия живёт в `manifest.json`, а не в файлах правил (см. §8).

## 2. Схема файла правил

Файл — JSON-объект. **Корень обязан быть объектом**; битый JSON и лишние поля — ошибка
загрузки, а не предупреждение (ADR-008: набор приходит из сети и управляет удалением файлов).

| Поле | Тип | Обяз. | Значение |
|---|---|---|---|
| `schemaVersion` | число | **да** | Версия схемы. Поддерживается только `1`; любое другое значение — отказ от набора |
| `rules` | массив объектов | **да** | Список правил. Пустой набор — ошибка (`набор правил пуст`) |
| `version` | строка | нет | Версия набора. Допустимо, но **не является источником истины**: при склейке нескольких файлов берётся значение из первого файла (`loadRuleFiles` в `core/rules.cpp`). Версию набора ведём в `manifest.json` (§8) |
| `minAppVersion` | строка | нет | Минимальная версия приложения, для которой набор валиден. Проверяется при обновлении из сети |

Неизвестное поле на уровне файла → `неизвестное поле "<имя>"`.

Минимальный **валидный** файл — одна категория, одно правило:

```json
{
  "schemaVersion": 1,
  "version": "2026.02.1",
  "minAppVersion": "1.0.0",
  "rules": [
    {
      "id": "temp.system",
      "category": "temp.system",
      "safety": "safe",
      "locator": "C:\\Windows\\Temp\\**",
      "minAgeDays": 7,
      "title": {"ru": "Временные файлы системы", "en": "System temporary files"},
      "note": "Порог 7 дней (SPEC §4 FR-3): незавершённые операции установщиков не трогаем."
    }
  ]
}
```

Пустой `rules` — не валидный набор (`набор правил пуст`), а не «минимальный файл».

## 3. Схема правила

Каждый элемент массива `rules` — объект с полями ниже. Неизвестное поле → ошибка загрузки.

| Поле | Тип | Обяз. | По умолч. | Значение и ограничения |
|---|---|---|---|---|
| `id` | строка | **да** | — | Идентификатор правила. Только строчные латинские буквы, цифры и `.` `_` `-`, длина 1–64. Уникален **во всём объединённом наборе**, не только в файле |
| `category` | строка | **да** | — | ID категории из SPEC §4 FR-3 — по нему строятся дерево и агрегаты на экране «Очистка» (FR-5). Не изобретайте свои: см. §7 |
| `safety` | строка | **да** | — | `safe` \| `review` \| `risky`. Других значений нет (SPEC §4 FR-4) |
| `locator` | строка | **да** | — | Шаблон пути (glob) с `%ПЕРЕМЕННЫМИ%`. Подробно — §4 и §5 |
| `locatorExcludes` | массив строк | нет | `[]` | Шаблоны, которые вырезаются из `locator`. Каждый — тот же синтаксис, что и `locator` |
| `minAgeDays` | число ≥ 0 | нет | `0` | Возрастной порог в днях по времени записи. `0` — «файлы любого возраста» |
| `requiresProcessesClosed` | массив строк | нет | `[]` | Имена процессов, которые держат файлы: кандидат уходит в «пропущено (занято)», пользователю предлагается закрыть их (`RmShutdown`, FR-6) |
| `groupByProfile` | булево | нет | `false` | Группировать результат по профилю (каталог верхнего уровня под `locator`) — для браузеров и почты |
| `title` | объект `{ru, en}` | нет | — | Название для UI. Оба языка желательны; в отсутствие `ru` показывается `en` |
| `note` | строка | нет | — | Пояснение для пользователя: что это и чем за это платим. Пишется на русском |

Эталонный пример из SPEC §4 FR-4 (в наборе он разложен на отдельные правила по подкэшам):

```json
{
  "schemaVersion": 1,
  "rules": [
    {
      "id": "browser.cache.edge",
      "category": "browser.cache",
      "safety": "safe",
      "locator": "%LOCALAPPDATA%\\Microsoft\\Edge\\User Data\\*\\Cache\\**",
      "locatorExcludes": ["**/Service Worker/ScriptCache/**"],
      "minAgeDays": 0,
      "requiresProcessesClosed": ["msedge"],
      "groupByProfile": true,
      "title": {
        "ru": "Кэш Microsoft Edge",
        "en": "Microsoft Edge cache"
      },
      "note": "Одноразовые данные: следующий заход на сайт скачает страницу заново."
    }
  ]
}
```

### 3.1. Проверки, которые ломают загрузку

Список полный — он вызывается при каждой загрузке набора:

1. Корень не объект, `rules` не массив, `schemaVersion != 1`.
2. Неизвестное поле (в файле, в правиле, в `title`).
3. `id` не строка, длиннее 64 символов, содержит символ вне `[a-z0-9._-]`.
4. `safety` не `safe|review|risky`.
5. Некорректный шаблон в `locator` или в любом элементе `locatorExcludes` (например, непарная `[`).
6. `minAgeDays` — не число или отрицательное.
7. `locatorExcludes`, `requiresProcessesClosed` — не массив строк.
8. `title` — не объект; `note` — не строка.
9. **Правило `safe` без возрастного порога и без узнаваемого имени каэша.** Движок требует, чтобы
   `safe`-правило было узким: `minAgeDays >= 1` **либо** в `locator` есть подстрока `Cache`, `cache`,
   `Temp` или `temp`. Иначе — ошибка `safe без minAgeDays и без вхождения Cache/Temp — слишком
   широкое, используйте review`. Смысл проверки: `safe` — это обещание, которое движок обязан
   уметь подтвердить; «удалять наугад, но верить, что это кэш» не является обещанием.
10. Дублирующийся `id` в объединённом наборе.
11. Набор пуст.

Ошибка на любом из этих пунктов означает: **старый рабочий набор остаётся в силе**, в лог пишется
причина, приложение продолжает работу (SPEC §9.2, шаг 4). Приложение никогда не остаётся
без набора правил.

## 4. Шаблоны путей (`locator`)

Сопоставление реализовано в `core/glob.cpp`, переносимо и не зависит от Windows API.
Сравнение регистронезависимое (ASCII), разделители `\` и `/` нормализуются в `/` — правило
можно писать и проверять на Linux, и на Windows.

| Символ | Значение |
|---|---|
| `*` | Любая последовательность **внутри одного сегмента**. Границу каталога не пересекает: `%TEMP%\*.log` не матчит `sub\a.log` |
| `**` | Любая последовательность, включая разделители. `a\**\b` совпадает и с `a\b`, и с `a\x\y\b` |
| `?` | Ровно один символ, не разделитель |
| `[abc]`, `[a-z]`, `[!abc]`, `[^abc]` | Класс символов, без разделителей. `!` и `^` — отрицание |
| любой другой символ | Литерал |

Практические следствия для `locator`:

- Один каталог целиком: путь без всяких шаблонов — `C:\Windows\WinSxS`.
- Содержимое каталога: путь + `\*` (файлы верхнего уровня) или `path + \**` (рекурсивно).
- Все профили браузера: `User Data\*\Cache\**` — одиночный `*` не залезет в подкаталог профиля.
- Рекурсия с сохранением «хвоста»: `...\Cache\**\*.log` — вложенные файлы с нужным расширением.

### 4.1. Подстановка `%ПЕРЕМЕННЫХ%`

`%ИМЯ%` подставляется значение из карты окружения, которую наполняет платформенный слой
(`GetEnvironmentVariableW`). **Переменная, которой нет в карте, остаётся в шаблоне как есть**
(`%APPDATA%\...`), а набор помечается как частично неразрешённый: приложение покажет
«часть правил неактивна». Правило с неразрешённой переменной просто не сработает — это не ошибка.

Рекомендации по записи путей (выведены из набора и особенностей Windows):

- `%LOCALAPPDATA%`, `%USERPROFILE%`, `%TEMP%`, `%APPDATA%`, `%ProgramData%`, `%ProgramFiles%`,
  `%SystemDrive%` — переменные, уже используемые в наборе.
- Профили и данные приложений лежат в разных деревьях: Firefox/Thunderbird и Opera — в роуминге
  (`%USERPROFILE%\AppData\Roaming\...`), Chromium-браузеры и кэши DirectX — в
  `%LOCALAPPDATA%`. Пока платформенный слой не отдаёт `%APPDATA%` в карте окружения, для
  роуминга пишем путь литералом `%USERPROFILE%\AppData\Roaming\...` — так правило работает
  при любой карте окружения. Если переменная всё же не раскрылась, **выдумывать путь нельзя**:
  это ложные кандидаты, а они бьют по G3 («очистка ничего не ломает»).
- Системные каталоги Windows пишем литералом `C:\Windows\...` (§7.1): буква диска в
  системных путях стабильнее переменной, а `%SystemDrive%` используем там, где путь
  действительно зависит от диска системы (корзина всех томов).

### 4.2. Экранирование в JSON

Разделитель пути в JSON — `\\`. То есть Windows-путь `%LOCALAPPDATA%\Temp` записывается
как `"%LOCALAPPDATA%\\Temp"`, а одиночный `\` в JSON недопустим и сделает файл битым.

## 5. Уровни безопасности: что можно чистить безопасно

`SafetyLevel` — это обещание пользователю, и уровень выбирается по **последствиям для данных**,
а не по удобству реализации (SPEC §4 FR-4). Уровень влияет на три вещи: показывается ли
элемент по умолчанию, спрашивается ли подтверждение, идёт ли удаление через корзину приложения
(FR-7) или напрямую.

| Уровень | Что это значит | Поведение в UI |
|---|---|---|
| `safe` | Данные одноразовые: приложение восстановит их само. Цена — время или повторная загрузка | Включено по умолчанию, без подтверждения |
| `review` | Данные пользователя или ценны, но восстановимы. Возможна потеря необратимого (сохранённые пароли, история) | **Выключено по умолчанию**, удаление только по явному подтверждению, через корзину приложения |
| `risky` | Удаление почти наверняка необратимо или ломает систему/другое ПО. Обычно правило ничего не удаляет, а только оценивает | **Скрыто по умолчанию**: видно только через «показать все» с двойным подтверждением |

### 5.1. Что относится к `safe`

Основание — SPEC §4 FR-3. Здесь и далее: цена очистки, а не «файл временный по имени».

| Категория | Почему безопасно | Чем платим |
|---|---|---|
| `temp.user`, `temp.system` | Распакованные установщики и промежуточные данные, которые приложения не хранят после завершения операции | Порог 2 и 7 дней: незавершённые операции не трогаем. Деинсталляторы (`unins*.exe`) исключены |
| `recycle.bin` | Пользователь уже решил, что файл выбросил | Показать объём отдельно, до подтверждения |
| `browser.cache`, `firefox.cache` | HTTP-кэш, Code Cache, GPUCache, DawnCache, `Old/`, `blob_storage`: одноразовые данные, страница скачается заново | Нужен закрытый браузер → `requiresProcessesClosed`; тяжёлые сайты дольше открываются в первый раз |
| `ms.update` | `SoftwareDistribution\Download` — уже применённые обновления | На время операции останавливается служба |
| `wer`, `logs` | Отчёты об ошибках и журналы, ценные для разбора, а не для работы системы | Порог 14 дней, чтобы не съедать «свежий» материал |
| `icon.font.cache`, `shadercache`, `thumbnails` | Кэши иконок, шрифтов и эскизов пересоздаются ОС | Первый запуск после очистки чуть медленнее |

### 5.2. Что не может быть `safe`

| Категория | Почему не `safe` |
|---|---|
| `browser.history` | Cookies, Login Data, Web Data, история — это **не кэш**: их не восстановить без учётных данных пользователя |
| `prefetch` | Удаление не даёт выигрыша, а ухудшает запуск программ и отладку. Выключено по умолчанию |
| `delivery.opt` | `SoftwareDistribution\DeliveryOptimization` и кэш DoSvc: с ними связана peer-доставка обновлений, цена ошибки выше, чем у обычного кэша |
| `crash.dumps`, `memory.dumps` | Дампы нужны для разбора аварий; старые `.dmp` — `review` с порогом 30 дней |
| `user.bigfiles`, `npm.pip.cache` | Это данные пользователя (загрузки, документы, видео) или содержимое рабочих кэшей менеджеров пакетов. `review`, через корзину приложения |
| `installer.cache` | `C:\Windows\Installer` — удаление ломает uninstall/repair. Только оценка, `risky` |
| `winsxs.report` | WinSxS вручную не чистится. Только оценка через `DISM /AnalyzeComponentStore`, `risky` |
| `wsl.vhdx.report` | Файл `ext4.vhdx` — это весь дистрибутив/контейнеры: удаление равносильно потере гостевой системы. Только оценка, `risky` |

### 5.3. Приём «только оценка»

Для категорий, которые нельзя чистить (WinSxS, Installer, образы VHDX), используется один приём:
`locator` **без шаблонов** — путь к каталогу или файлу целиком. Движок не перечисляет содержимое
для удаления даже при «показать все» и двойном подтверждении; провайдер категории запускает
внешнюю процедуру оценки (DISM, `docker system df`, оценка аллоцированного размера VHDX) и
показывает результат в отчёте. Правило остаётся `risky` и скрытым по умолчанию.

Место для освобождения места в таких случаях описывается в `note` — вместе с порядком команд
(`wsl --shutdown` перед сжатием, `docker system prune` перед `Optimize-VHD`). Пользователь должен
получить правильный порядок из приложения, а не из поисковика.

### 5.4. Чего не делаем никогда

Жёсткие запреты, независимо от уровня (SPEC §2, §4 FR-6, §10):

- Не чистим реестр, автозагрузку, программы, дефрагментацию, SMART, планировщик, учётные записи
  и облако — это не-цели MVP (§2) и будущие версии.
- Не пишем правила на `%WINDIR%`-внутренние каталоги компонентов и не трогаем `C:\Windows\Installer`,
  `WinSxS`, `System Volume Information` вручную.
- Не удаляем то, что не описано правилом: путь, не совпавший ни с одним правилом, не удаляется
  никогда («белый список неизвестного», §10).
- Не удаляем за пределами корня, заданного `locator`, и не идём по reparse-точкам (FR-6).
- Не выдумываем путь, если переменная окружения не раскрылась: лучше неактивное правило,
  чем ложный кандидат.

## 6. Как добавить правило в существующую категорию

1. **Проверить, что каталога правда нет в наборе.** Часто нужен не новый `id`, а `locatorExcludes`
   или отдельный каталог в том же файле. Правил «на всё» быть не должно: широкий `safe`-locator
   без `minAgeDays` движок не примет (§3.1, п. 9).
2. **Выбрать `id`** по конвенции: `<категория>.<вариант>`, где вариант — браузер, каталог или
   группа профилей: `browser.cache.edge`, `browser.cache.edge.gpu`, `temp.user.env`.
   Только `[a-z0-9._-]`, уникально во всём наборе.
3. **Написать `locator`** от общего к частному: сначала точный каталог, потом `*`/`**` по
   профилям, в конце `**`, если нужно рекурсивно. Проверить, что `*` не расползается на
   соседние каталоги: `User Data\*\Cache\**` безопасен, `User Data\**` — нет.
4. **Вынести исключения в `locatorExcludes`**: деинсталляторы, `desktop.ini`, `Thumbs.db`,
   незавершённые загрузки (`*.crdownload`, `*.part`, `*.partial`), рабочие файлы Office (`~$*`).
   Исключения проверяются после совпадения и всегда выигрывают у `locator`.
5. **Проставить уровень и пороги:** `safety` по §5, `minAgeDays` из SPEC §4 FR-3 или с запасом,
   `requiresProcessesClosed` — если файлы держит приложение.
6. **Написать `title`** на двух языках и **`note`** — что это, чем платим, что **не** входит
   в правило. `note` читает пользователь, это объяснение, а не комментарий для разработчика.
7. **Проверить на дубли и пересечения:** два правила с пересекающимися `locator` дадут один и тот же
   файл в двух очистках. Смежные категории (`icon.font.cache` против `thumbnails`,
   `shadercache` против `browser.cache.*.gpu`) должны быть непересекающимися.
8. **Прогнать проверки** (§9) и приложить изменение к набору одним коммитом с `manifest.json`
   и подписью (§8).

## 7. Как добавить новую категорию

1. **Проверить, что это не не-цель.** Если идея про реестр, автозагрузку, SMART или облако —
   она не входит в MVP (§2, §3) и правилом не выражается.
2. **Внести строку в SPEC §4 FR-3**: ID категории, что чистим, источник, риск, примечание.
   Категория без строки в SPEC считается незавершённой: её не будет ни в дереве UI, ни в
   критериях приёмки.
3. **Придумать ID:** он же `category` в правилах, он же имя файла `rules/<категория>.json`.
   Строчные буквы, цифры, точка — как в `id` правила. Идентификаторы уже принятой категории
   не переименовываются: это ломает пользовательские настройки вкл/выкл (FR-9).
4. **Определить уровень** по §5. Категория, которую нельзя чистить, сразу проектируется
   как «только оценка» (§5.3): это честнее, чем изобретать способ «осторожно удалить часть».
5. **Продумать исключения до первой строки `locator`.** Самая частая ошибка нового правила —
   слишком широкий шаблон, который задевает пользовательские данные рядом.
6. **Написать правила** (§6) и `note` с ценой очистки.
7. **Обновить `manifest.json`**: новая запись в `files` с `sha256` и `size`, бамп `version`,
   переподпись (§8). Версия набора в `manifest.json`, не в файлах правил.
8. **Прогнать §9**, отдать на ревью по чек-листу §10.

### 7.1. Категории-расширения набора

Иногда набор пополняется категорией, которой нет в SPEC §4 FR-3 (например, `wsl.vhdx.report`).
Такое расширение допускается только по образцу уже существующих оценочных категорий
(`winsxs.report`, `installer.cache`) и обязано:

- быть `risky` и скрытой по умолчанию;
- ничего не удалять — только оценивать (приём §5.3);
- описывать в `note` правильный порядок команд для освобождения места;
- быть отмечена в `note` как расширение набора, с указанием, какой категории подражает,
  — чтобы её отсутствие в FR-3 не выглядело ошибкой.

## 8. Версия набора, манифест и подпись

`rules/` — недоверенный вход: подменённый набор правил — это вектор удаления данных
(ADR-008, SPEC §9.2). Поэтому набор версионируется и подписывается.

### 8.1. `rules/manifest.json`

| Поле | Тип | Обяз. | Значение |
|---|---|---|---|
| `schema` | число | **да** | Версия схемы манифеста (имя поля — как в §9.2) |
| `schemaVersion` | число | нет | Синоним `schema`; если заданы оба — обязаны совпадать, иначе ошибка |
| `version` | строка | **да** | Версия набора, например `2026.02.1` |
| `minAppVersion` | строка | нет | Минимальная версия приложения, для которой набор валиден |
| `files` | массив объектов | **да** | Список файлов набора |
| `files[].path` | строка | **да** | Имя файла относительно `rules/`, например `temp.user.json` |
| `files[].sha256` | строка | **да** | SHA-256 содержимого файла в hex |
| `files[].size` | число | **да** | Размер файла в байтах |

Неизвестное поле в манифесте или в его элементе — та же ошибка, что и в правиле: набор
не применяется.

### 8.2. Порядок обновления (проверяется со стороны приложения, ADR-008)

1. Раз в сутки `GET` по HTTPS за `manifest.json` + `rules.sig` по закреплённому тегу
   (`rules/vX.Y`). Только `GET`, без кук и авторизации, таймаут 10 с.
2. Проверка: схема манифеста → `minAppVersion` ≤ текущей версии → подпись Ed25519 встроенным
   в бинарник публичным ключом → SHA-256 каждого файла.
3. Только после этого файлы качаются в staging, проверяются парсером и **атомарно**
   подменяют рабочий набор.
4. Любая ошибка → тихий отказ с записью в лог, приложение работает на предыдущем наборе.
   Пользователь всегда может вернуть встроенный набор.

Следствие для автора правила: **набор нельзя править «по-тихому»**. Изменился файл — изменились
`files[].sha256` и `size`, поднялась `version`, нужна новая подпись. Частая ошибка релиза —
новое правило в наборе, но манифест не пересобран: сработает откат, и правило не применится.

Приватный ключ подписи хранится вне репозитория (§9.2); в набор он не попадает никогда.

## 9. Проверка правок

Правила — данные, но они исполняются движком, поэтому проверка идёт полным конвейером,
и только его штатными скриптами (другой тулчейн даёт недостоверный результат):

```
tools\build.bat Debug
tools\test.bat Debug
```

Из WSL — то же самое, через `cmd.exe`:

```
cmd.exe /c "tools\build.bat Debug"
cmd.exe /c "tools\test.bat Debug"
```

Что покрыто проверками:

| Проверка | Где |
|---|---|
| Загрузка валидного файла, отказ на неизвестном поле | `tests/unit/core_tests.cpp` (`rules_loadsValidFile`, `rules_rejectsUnknownField`) |
| Неверный `id`, неверный `safety` | `rules_rejectsBadIdAndSafety` |
| Неверная версия схемы | `rules_rejectsWrongSchemaVersion` |
| Слишком широкое `safe`-правило | `rules_rejectsTooBroadSafeRule` |
| Склейка файлов и подстановка `%ПЕРЕМЕННЫХ%`, неразрешённые переменные | `rules_mergesFilesAndExpandsEnvironment`, `rules_reportsUnresolvedEnvironment` |
| Дубли `id` | `rules_rejectsDuplicateIds` |
| Синтаксис шаблонов, классы символов, `**` через сегменты | тесты `glob` в тех же юнит-тестах |

Перед отправкой на ревью полезно собрать набор вручную и убедиться, что он грузится целиком:
пустой набор, неизвестное поле или дубль `id` откатят **весь** набор, а не только плохой файл.

## 10. Чек-лист ревью правила

- [ ] `id` в конвенции `<категория>.<вариант>`, уникален во всём наборе.
- [ ] `category` — существующая категория из SPEC §4 FR-3 (или оформленное расширение §7.1).
- [ ] `safety` соответствует последствиям для данных (§5), а не названию каталога.
- [ ] `safe` правило проходит проверку узости: `minAgeDays >= 1` либо `Cache`/`Temp` в `locator`.
- [ ] `locator` максимально узкий: `*` не пересекает границу каталога, `**` — только там, где
      нужна рекурсия, шаблон не задевает соседние данные пользователя.
- [ ] `locatorExcludes` закрывает исключения (незавершённые загрузки, служебные файлы,
      деинсталляторы) — и это проверено, а не задумано.
- [ ] `minAgeDays` не меньше значения из FR-3; для пользовательских данных — с запасом.
- [ ] `requiresProcessesClosed` перечисляет реальные процессы-держатели.
- [ ] Нет пересечений с другими правилами: один файл не попадает в две очистки.
- [ ] Пути Windows записаны с `\\`; системные пути — литералом `C:\...`; переменные окружения
      реально поддерживаются платформенным слоем.
- [ ] `title` на `ru` и `en`, `note` объясняет цену очистки и что в правило **не** входит.
- [ ] `manifest.json` пересобран: `files[]` пополнен, `sha256`/`size` верны, `version` поднята.
- [ ] `tools\build.bat Debug` и `tools\test.bat Debug` проходят.
- [ ] `Risky`/`Review` не включены по умолчанию (поведение задаёт уровень, не код).
