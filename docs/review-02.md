## 3. Находки

### F-01. Отбор правила не является набором удаляемого: удаляется корень целиком

**Вердикт: ОБХОД ПОДТВЕРЖДЁН. Влияние: критическое (потеря данных внутри корня правила,
в том числе свежих и явно исключённых файлов).**

Где: `src/engine/candidate_collector.cpp:355-397` (`RootScan::visit`), `:382-393`
(возрастной фильтр), `:367-381` (исключения), `:815` (`candidate.path = rootPath`),
`:832-840` (причины в отчёте), `src/core/plan.cpp:252-262` (выбор действия),
`src/engine/executor.cpp:879-929` (`deleteItem` → `vfs::deleteTree(pathWide)`, строка 929),
`src/engine/executor.cpp:970-1000` (`trashItem` → `stageTrashItem` по пути корня, строка 993).

Суть. Единица кандидата — **каталог-корень**, а не отобранные файлы. Разбор локатора
даёт корень: для `%LOCALAPPDATA%\Temp\**` последний сегмент `**` означает «всё
содержимое корня» (`candidate_collector.cpp`, ветка `lastIsDoubleStar`), поэтому
`LocatedRoot.path` = `C:\Users\<user>\AppData\Local\Temp`, `leafPattern` пуст, и
`candidate.path` = весь этот каталог. Дальше обход дерева (`RootScan::visit`)
считает файлы, и **все** фильтры правила применяются только к счёту:

```
if (rule->excluded(entry.path)) { ++tally.excludedFiles; return Continue; }   // :367-381
if (ageFilter) { if (entry.writeTime > oldestAllowed) { ++tally.tooYoung; return Continue; } }  // :382-393
```

Ни один из этих `return Continue` не меняет множество, которое удалит исполнитель:
`CleanupExecutor::deleteItem` получает `item.path` = `candidate.path` и для каталога
вызывает `vfs::deleteTree(pathWide, ...)` (`executor.cpp:929`), а действие `Trash`
переносит тот же каталог целиком (`stageTrashItem`, `executor.cpp:993`). Слой
удаления о правилах не знает вообще: он получает только `DeleteOptions.allowedRoot`.

Что из этого следует на поставленном наборе (все локаторы с `**` в конце дают корень-каталог):

| Правило | Обещание в заметке правила | Что удалит исполнитель |
|---|---|---|
| `temp.user` | «Порог 2 дня — свежие файлы не трогаем»; «исключены `unins*.exe` и `is-*.tmp`» | всё дерево `%LOCALAPPDATA%\Temp`, включая файлы минутной давности и оба исключённых шаблона |
| `user.bigfiles.documents` | «Исключены временные файлы Office (`~$*`) и служебные»; возраст 90 дней | весь каталог `%USERPROFILE%\Documents` |
| `recycle.bin.allvolumes` | «Порог 1 день: элемент, удалённый пять минут назад, пользователь может восстановить сам» | всё дерево `%SystemDrive%\$Recycle.Bin` |
| `browser.cache.chrome.old` | minAgeDays 1 | весь каталог `Old` профиля |

Хуже всего то, что **отчёт говорит обратное**. Счётчики попадают в `reasons`
(`candidate_collector.cpp:832-840`): «по возрасту отсечено файлов: 412»,
«исключено правилом элементов: 3». Человек читает это как «эти файлы оставлены в
покое» — это правда только про арифметику объёма, а не про операцию. §12 требует,
чтобы ни один элемент не удалялся без видимого объяснения; объяснение здесь есть,
но оно описывает не то, что произойдёт.

Почему это обход, а не дефект оценки. Проверки FR-6 в фазе A (`executor.cpp:542-575`)
доказывают, что путь внутри корня правила и не защищён белым списком, — но они
оперируют **путём кандидата**, то есть тем же каталогом. Граница «внутри корня
правила» соблюдена, а граница «только то, что правило отобрало» не существует ни в
одном слое.

Что делать.
1. Сделать единицей операции набор файлов, а не корень: `LocatedRoot`/`CleanupCandidate`
   должны нести отобранные пути (или их потоковую выборку для отчёта), а исполнитель —
   удалять по списку. Для дерева в десятки тысяч файлов это требует либо второго
   прохода «собрать список → показать в dry-run → удалить список», либо
   повторного применения правила на фазе C (правило уже есть в `ChecklistOptions::rules`).
2. Как немедленная мера (одна проверка, не переписывание): если у правила включён
   возрастной фильтр или есть исключения, а при обходе отсечено хотя бы одно
   содержимое (`tally.tooYoung > 0 || tally.excludedFiles > 0 || tally.prunedDirs > 0`),
   — **не** выпускать кандидат как операцию дерева: пометить его «требует перечисления»
   и выполнять пофайлово, иначе отсечённое содержимое будет удалено вместе с
   корнем. Как минимум — формулировка причин в отчёте должна говорить «не учтено в
   оценке», а не «отсечено», пока мера не сделана.
3. Тест: правило `%LOCALAPPDATA%\Temp\**`, minAgeDays 2, в каталоге лежат файл двухлетней
   давности и файл минутной давности; ожидание — в операции только первый.

Нарушение спеки: §4 FR-3 (min age 2 дня / 7 дней / 14 дней / 30 дней / 90 дней),
FR-7 («проверка, что путь внутри ожидаемого корня правила» в связке с набором
удаляемого), §12 («100 % удалённых файлов восстанавливаются» — не для тех файлов,
которые правило не считало), §10 (критический риск «Повреждение системных данных при
ошибке в правиле»).

### F-02. Категория `user.bigfiles` удаляет пользовательские данные по умолчанию и без корзины

**Вердикт: ОБХОД ПОДТВЕРЖДЁН. Влияние: критическое (безвозвратная потеря документов,
загрузок, записей экрана).**

Где: `rules/user.bigfiles.json` (5 правил), `src/core/plan.cpp:201-265`,
`src/core/plan.hpp:34` (`kTrashDirectDeleteBytes = 100 МБ`), `src/core/scoring.cpp:44-48`.

Пять правил набора указывают прямо на пользовательские данные:

| Правило | Уровень | minAge | Корневой каталог |
|---|---|---|---|
| `user.bigfiles.downloads` | review | 90 | `%USERPROFILE%\Downloads` |
| `user.bigfiles.videos` | review | 90 | `%USERPROFILE%\Videos` |
| `user.bigfiles.documents` | review | 90 | `%USERPROFILE%\Documents` |
| `user.bigfiles.desktop` | review | 90 | `%USERPROFILE%\Desktop` |
| `user.bigfiles.profile-root` | review | 90 | корень профиля (файлы верхнего уровня) |

Заметки правил обещают: «Пользовательские данные, а не мусор: уровень review,
элемент не удаляется без явного подтверждения, операция идёт через корзину
приложения и отменяема (FR-7)». Ни одно из двух обещаний не обеспечено кодом.

*Отбор по умолчанию.* `decideCandidate` (`plan.cpp:201-265`) фильтрует по уровню
только в профиле `safe-only`. Профиль по умолчанию — `Recommended`
(`plan.hpp:61`), а в нём единственный фильтр — `confidence >= 50` (`plan.hpp:62`,
`kDefaultConfidenceThreshold = 50`). Уверенность кандидата `user.bigfiles.documents`
по `scoring.cpp` равна **100**: возраст проверен (все учтённые файлы ≥ 90 дней, штрафа
нет), блокировок нет, каталог не системный, «внутри профиля» штрафуется только для
`safe` (`scoring.cpp:44-48`), шаблон `…\Documents\**` не считается широким
(`scoring_bridge::isBroadLocator` отбрасывает `**` и смотрит на `Documents`), объём
заведомо больше 64 КБ. 100 ≥ 50 → элемент выбран по умолчанию.

*Куда именно.* `decideCandidate` (`plan.cpp:252-262`) не смотрит на уровень
безопасности вовсе: при `allocatedBytes > trashDirectDeleteAboveBytes` (100 МБ) действие —
`Delete`, то есть прямое удаление без корзины и без отмены. Категория существует
именно ради крупных файлов, поэтому «больше 100 МБ» для неё — норма, а не исключение.

Проверено на штатном бинарнике (слот `a92`, `mrproper-cli plan --json`, профиль по
умолчанию, §5, прогон 2):

```
delete  review  conf 100  Крупные файлы: документы     1.50 GiB | выбран по умолчанию; объём больше 105 МБ — прямое удаление
delete  review  conf 100  Крупные файлы: рабочий стол  3.00 GiB | выбран по умолчанию; объём больше 105 МБ — прямое удаление
trash   safe    conf  85  Временные файлы пользователя          | выбран по умолчанию; удаление через корзину приложения
```

*Порога «больше 1 ГБ» в коде нет.* FR-3 определяет категорию как «Файлы > 1 ГБ,
старше 90 дней, вне системных каталогов». Заметки правил честно признают, что поля
размера в схеме нет, и отправляют порог «провайдеру сканера» — но `src/scanner/`
пуст, провайдеров категорий в проекте нет (единственный сборщик — `candidate_collector`,
он размер не фильтрует), константы 1 ГБ в коде тоже нет (проверено поиском). То есть
правило срабатывает на **все** файлы каталога старше 90 дней, а не на крупные; вместе
с F-01 кандидат — это весь каталог целиком.

*Восстановление.* G3 и §12 обещают «100 % удалённых файлов восстанавливаются из
корзины приложения». Для этой категории обещание не выполняется по построению: всё
крупнее 100 МБ уходит прямым `Delete`.

Что делать.
1. Правилу-флагу или категории `user.bigfiles` — принудительный `Trash` независимо от
   объёма, с отказом от прямого удаления (это ровно тот случай, для которого FR-7
   даёт исключение «большие кэши», а не пользовательские файлы).
2. Профиль `Recommended` не должен выбирать `review` по умолчанию (см. F-03), а для
   категории `user.bigfiles` — требовать подтверждения по категории с показом числа
   файлов и байт до подтверждения.
3. Либо ввести в схему правил поле минимального размера (и проверять его в
   `candidate_collector` рядом с min-age), либо оформить порог 1 ГБ как отдельного
   провайдера категории; до этого привести заметки правил в соответствие с поведением
   (обещание, которого нет, в заметке опаснее, чем отсутствие обещания).

Нарушение спеки: §4 FR-3 (категория `user.bigfiles`), FR-7 (корзина, отмена), G3,
§12 («100 % удалённых файлов восстанавливаются из корзины приложения»).

### F-03. У уровня `review` нет семантики «выключено по умолчанию»

**Вердикт: ОБХОД ПОДТВЕРЖДЁН. Влияние: высокое (уровень риска не влияет на отбор).**

Где: `src/core/plan.cpp:201-265` (`decideCandidate`), `src/core/plan.hpp:61-62`,
`rules/browser.history.json`, `rules/prefetch.json`, `rules/delivery.opt.json`.

FR-3 требует для трёх категорий именно «выключено по умолчанию»:

* `browser.history` — «**выкл. по умолчанию, с явным подтверждением**»
  (39 правил, среди них `Login Data*` — база сохранённых паролей, `Cookies*`,
  `Web Data*` — автозаполнение и карты);
* `prefetch` — «**выкл. по умолчанию**»;
* `delivery.opt` — «Review» (то же поведение, что и у остальных `review`).

В коде единственный механизм «по умолчанию не берём» — это `Risky` (скрыт,
`plan.cpp:215-219`) и порог уверенности 50 (`plan.cpp:244`). Уровень `review` при
профиле `Recommended` не фильтруется вовсе, а уверенность у этих правил высокая:
у `browser.history.*` — 80 (штраф 20 за «широкий» шаблон `Login Data*`, остальное
чисто), у `prefetch.*` — 80, у `npm.pip.cache.*` и `recycle.bin` — 100. Проверено на
штатном бинарнике (прогон 3):

```
trash  review  conf 80   Пароли и автозаполнение Chrome    | выбран по умолчанию; удаление через корзину приложения
trash  review  conf 80   Prefetch Windows                   | выбран по умолчанию; удаление через корзину приложения
delete review  conf 100  NuGet: глобальная папка пакетов    | выбран по умолчанию; объём больше 105 МБ — прямое удаление
delete safe   conf 100  Корзина                             | выбран по умолчанию; объём больше 105 МБ — прямое удаление
```

То есть «выкл. по умолчанию» из FR-3 — это текст заметки и UI-галочки, а не поведение
движка. План, который человек увидит на экране «Очистка» сразу после скана, уже
содержит удаление паролей браузера.

Что делать. В `SelectionProfile::Recommended` не выбирать `Review` (оставить его для
ручного выбора), либо добавить в опции плана «максимальный уровень по умолчанию» со
значением по умолчанию `Safe`. Отдельно: FR-3 для `browser.history` просит «явного
подтверждения» — это подтверждение уровня категории, а не галочка у каждого из
39 правил; его удобно сделать одним действием «подтверждаю очистку истории и паролей
браузеров» с перечислением того, что исчезнет (файлы `Login Data`, `Cookies`,
`Web Data` — по числу и размеру).

Нарушение спеки: §4 FR-3 (`browser.history`, `prefetch`, `delivery.opt`), FR-4
(«`Review`/`Risky` по умолчанию выключены» — формулировка митигации в §10),
§12 («`Risky` по умолчанию скрыты» — для `Review` в §12 обещания нет, но FR-3 требует).

### F-04. «Только оценка» в правилах не обеспечено ничем

**Вердикт: ОБХОД ПОДТВЕРЖДЁН. Влияние: высокое (удаление образа ВМ = потеря всего
внутри).**

Где: `rules/winsxs.report.json`, `rules/wsl.vhdx.report.json`, `rules/dev.caches.json`
(категория `npm.pip.cache`), `src/core/plan.cpp:215-262`, `src/platform/vfs_delete.cpp:276-330`.

Заметки правил формулируют это как запрет:

* `winsxs.report` — «содержимое WinSxS не перечисляется для удаления **даже при
  «показать все» и двойном подтверждении**»;
* `wsl.vhdx.report.*` — «Оценка без удаления… простое удаление файла уничтожает все
  контейнеры и образы разом»;
* `npm.pip.cache.pip` — «пока элемент только в отчёте, удаление из приложения не
  предлагается».

В коде такого флага нет. `Risky` после `--allow-risky` становится обычным кандидатом,
а решение о действии принимает только объём (`plan.cpp:252-262`). Проверено на
штатном бинарнике (прогон 4):

```
delete risky conf 100 Хранилище компонентов WinSxS — только оценка   | выбран по умолчанию; объём больше 105 МБ — прямое удаление
delete risky conf 100 WSL: образы дистрибутивов из Microsoft Store   | выбран по умолчанию; объём больше 105 МБ — прямое удаление
```

Что спасает и что нет. `C:\Windows\WinSxS` и `C:\Windows\Installer` спасает белый
список платформенного слоя (`vfs_delete.cpp:305-320`, жёсткий запрет) — то есть
спасение приходит не от правила, а от другого механизма, и правило об этом не знает.
А вот `%LOCALAPPDATA%\Packages\<пакет>\LocalState\ext4.vhdx`,
`%LOCALAPPDATA%\Docker\wsl\**\*.vhdx` и `%USERPROFILE%\.nuget\packages` в белом
списке не значатся: `Delete` для них проходит, и за «подтверждением DELETE-RISKY»
стоит удаление всего дистрибутива WSL, всех образов Docker или всей офлайн-сборки
проектов. Заметка правила в этом месте — единственный барьер, а она — текст.

Что делать. Ввести в схему правил поле `estimateOnly` (неизвестное поле — ошибка
загрузки, `rules.cpp:59-64`, так что старый набор это не сломает) и проверять его в
`PlanBuilder::rebuild`: кандидат с `estimateOnly` всегда получает `Keep` и никогда не
попадает в `operations()` ни при каком профиле и подтверждении. Правила
`winsxs.report`, `wsl.vhdx.report.*` и оценка `npm.pip.cache` перевести на этот флаг;
для `Risky`-правил с локатором-каталогом без шаблонов — сделать флаг обязательным
(иначе ошибка загрузки), потому что «оценка каталога» и «удаление каталога» —
разные операции, и разница сейчас держится на заметке.

Нарушение спеки: §4 FR-3 (`winsxs.report`, `installer.cache`, `npm.pip.cache` —
«только в отчёте», «оценка только»), FR-4, §12.

### F-05. `safe` проверяется подстрокой, корень локатора не проверяется

**Вердикт: ОБХОД ПОДТВЕРЖДЁН (барьер — подпись, не валидация). Влияние: высокое
в модели угроз ADR-008; сегодня требует приватного ключа владельца.**

Где: `src/core/rules.cpp:131-141` (`Rule::fromJson`), `:245-256` (`validateRuleSet`),
`src/platform/rulesync_client.cpp:1420-1450` (проверка подписи → `loadVerifiedRuleSet`).

Единственный структурный фильтр «safe не должен быть широким» — наличие подстроки
`Cache`/`Temp`/`cache`/`temp` в локаторе либо `minAgeDays >= 1`:

```cpp
if (rule.safety == SafetyLevel::Safe && rule.minAgeDays < 1 &&
    rule.locator.find("Cache") == npos && rule.locator.find("Temp") == npos && ...) {
    throw RuleError(origin + ": правило " + rule.id + " объявлено safe, но …");
}
```

Ни корня локатора, ни категории, ни того, что путь ведёт в пользовательские данные,
валидация не проверяет. Правило
`{"id":"x","category":"tmp","safety":"safe","locator":"%USERPROFILE%\\Documents\\**","minAgeDays":1}`
проходит загрузку, `validateRuleSet` его не видит, и набор принимается. Дальше по
F-02/F-03 такой кандидат получает уверенность 100, выбирается по умолчанию и
удаляется прямым `Delete`.

Честная оценка угрозы. Реальный барьер здесь один и он настоящий: набор правил
подписывается Ed25519-ключом владельца, публичный ключ встроен в бинарник,
`policy.requireSignature = true` (строка 1422), неподписанный/подменённый набор
откатывается. То есть удалённый злоумышленник правило добавить
не может. Настоящая опасность в другом: (а) ошибка владельца при подписании
набора — подписывается то, что прошло те же слабые проверки; (б) импорт набора
вручную (FR-9, «импорт вручную» разрешён) идёт через тот же парсер; (в) §10 сам
называет этот класс риска критическим, а защита здесь — только подпись, без
независимой проверки содержимого.

Что делать.
1. Проверять корень структурно, а не подстрокой: белый список допустимых корней для
   `safe` (каталоги кэша под `%LOCALAPPDATA%`/`%APPDATA%`, `%TEMP%`, `C:\Windows\Temp`,
   `C:\Windows\Logs`, `%ProgramData%\<конкретный каталог>`), плюс жёсткий запрет для
   корней пользовательских данных (`Documents`, `Desktop`, `Downloads`, `Pictures`,
   `Music`, `OneDrive`, корень профиля) на **любом** уровне, включая `safe` и `review`.
2. Тот же список использовать в `Rule::fromJson` (загрузка) и в `executor::checkItem`
   (исполнение, строка 542) — две проверки, но одна истина; иначе правило, прошедшее
   загрузку до появления новой схемы, продолжит работать.

Нарушение спеки: §9.2/ADR-008 (набор правил — недоверенный вход, проверка должна быть
не только криптографической), §10 (критический риск «Подмена набора правил из сети»).

### F-06. Корни правил следуют за переменными окружения пользователя

**Вердикт: ОБХОД ПОДТВЕРЖДЁН. Влияние: среднее (путь правила задаётся пользователем,
уровень при этом `safe`).**

Где: `src/core/glob.cpp::expandEnvironment` (`rules.cpp:227-231` — вызов при загрузке),
`src/platform/rulesync_client.cpp:665-670` (`environmentDump()` →
`GetEnvironmentStringsW()`, строка 666), `rules/temp.user.json` (`temp.user.env`),
`rules/recycle.bin.json` (`%SystemDrive%`).

Подстановка переменных окружения в локатор — механизм правил, а не деталь: без него
`%LOCALAPPDATA%` не работает. Но источник значений — **весь блок окружения процесса**,
а не Known Folder API: это осознанное решение (комментарий в
`rulesync_client.cpp:609-614` — `GetEnvironmentVariableW` вместо
`SHGetKnownFolderPath`), и для `%LOCALAPPDATA%` оно безопасно. Для `%TEMP%` — нет:

* `temp.user.env` = `%TEMP%\\**`, уровень `safe`, `minAgeDays: 2`;
* `TEMP`/`TMP` — per-user переменные, задаваемые пользователем или скриптом
  (`setx`, `HKCU\Environment`, профиль CI, сторонние программы);
* если `TEMP` указывает на каталог с данными (например, на перенесённую на другой
  диск рабочую папку), всё дерево этого каталога старше двух дней становится
  кандидатом уровня `safe` — а по F-02/F-03 такой кандидат выбирается по умолчанию.

Дополнительно: неразрешённая переменная делает правило неактивным
(`candidate_collector.cpp`, `hasUnresolvedVariable` + `stats.rulesSkippedUnresolved`) —
это сделано правильно; но разрешённая и *неожиданная* переменная проходит так же
гладко, как ожидаемая, и ничем не отличается в отчёте.

Что делать. После раскрытия переменных проверять корень правила по белому списку
корней (тот же, что в F-05) и, если корень не распознан как каталог кэша/временная
папка, помечать правило неактивным с видимой причиной («корень %TEMP% не похож на
временную папку»), а не выпускать его кандидатом. Для `%SystemDrive%\\$Recycle.Bin`
и `%USERPROFILE%\\<известная папка>` whitelist должен быть явным списком правил,
а не угадыванием по подстроке.

Нарушение спеки: §10 (риск «Ошибка в правиле»), FR-4 (уровень `safe` как обещание),
ADR-002 (правила — данные; данные должны быть проверяемы).

### F-07. Вкл/выкл правила и смена уровня из настроек не доходят до скана

**Вердикт: НЕ ОБХОД, ДЕФЕКТ. Влияние: среднее (нет рабочего способа снять опасное
правило).**

Где: `src/ui/view_settings.cpp:496` (`std::map<std::string, RuleOverride> overrides`),
`:604-641` (`setRuleEnabled`, `requestSafety`), `src/ui/view_settings.hpp:344`.

Решения пользователя по правилам живут в `SettingsViewModel::Impl::overrides` — в
оперативной памяти одного объекта. Поиск по `src/` даёт: `SettingsViewModel` не
упоминается нигде, кроме `view_settings.cpp/.hpp`; карта `overrides` не сериализуется
ни в один файл и не читается ни сборщиком кандидатов, ни планировщиком. То есть
FR-9 («правила вкл/выкл, смена safety-уровня для конкретного правила») на сегодня —
экран без последствий.

Для этого ревью важно следствие: у пользователя **нет** способа выключить
`user.bigfiles.documents` насовсем. Снять галочку в плане можно, но на следующем
скане элемент снова придёт выбранным по умолчанию (F-02), а правило продолжит
приносить кандидатов. Рабочий обход сегодня — только правка набора правил на диске.

Что делать. Хранить решения в `%LOCALAPPDATA%\MrProper\rule-overrides.json` и применять
их в `scan_coordinator` до сбора кандидатов: `enabled = false` → правило не
разворачивается; `safety` ниже объявленного → кандидат не может получить `Delete`
(см. F-02, пункт 1) и не выбирается по умолчанию. Плюс тест: override `enabled=false`
→ правило не даёт кандидатов даже при скане вручную.

### F-08. Провайдеров, на которые ссылаются заметки правил, нет

**Вердикт: НЕ ОБХОД, ДЕФЕКТ. Влияние: среднее (обещание в пользовательском тексте
не обеспечено кодом).**

Где: `src/scanner/` (каталог существует, файлов нет), заметки
`rules/user.bigfiles.json`, `rules/recycle.bin.json`, `rules/winsxs.report.json`,
`rules/dev.caches.json`.

FR-3 и заметки правил отводят часть работы «провайдеру категории»:

| Обещание в заметке | Что в коде |
|---|---|
| `recycle.bin`: «перебор томов и выбор подкаталога текущего пользователя делает провайдер через SHQueryRecycleBin/IFileOperation» | провайдера нет; правило — обычный обход `%SystemDrive%\$Recycle.Bin\**` (это уже отмечено в ревью 01, F-04) |
| `user.bigfiles.*`: «порог „больше 1 ГБ“ задаёт провайдер сканера» | провайдера нет, константы 1 ГБ нет: кандидатом становится весь каталог |
| `winsxs.report`: «провайдер запускает DISM /Online /Cleanup-Image /AnalyzeComponentStore» | вызова DISM в `src/` нет (проверено поиском): кандидатом становится каталог `C:\Windows\WinSxS` целиком |
| `npm.pip.cache.pip`: «удаление из приложения не предлагается» | не «предлагается» ничем: это `review` с обычным отбором (F-03, F-04) |

Заметки правил — то, что пользователь читает в отчёте и в UI, то есть часть контракта.
Обещание, которого нет, хуже отсутствия обещания.

Что делать. Разделить задачи: (а) реализовать провайдеров (перебор томов для корзины,
размер для `user.bigfiles`, оценка DISM для WinSxS) — это отдельные задачи с тестами;
(б) до их готовки привести заметки в соответствие с фактическим поведением и
зафиксировать это в `docs/rules-authoring.md`, чтобы правило, обещающее провайдер,
нельзя было выпустить без него (например, обязательное поле `requiresProvider`).

### F-09. Пробелы в тестовом покрытии

**Вердикт: ПРОБЕЛ ПОКРЫТИЯ.**

* `tests/unit/rules_fuzz_tests.cpp:404` и `tests/unit/rules_manifest_tests.cpp:65`
  упоминают `user.bigfiles.downloads` только как пример корректного JSON — ничего

* Нет теста «отбор правила = множество удаляемого»: правило с `minAgeDays` и
  исключениями, в корне которого лежат и старые, и свежие файлы; ожидание — в
  операции только старые (закрывает F-01).
* Нет теста на отбор по умолчанию для `review`: кандидат уровня `review` с

* Нет теста «оценка без удаления»: правило с флагом «только оценка» не даёт

* Нет теста на корень правила из F-05: `safe`-правило с корнем

Минимальный набор одной задачей: четыре теста выше (второй и четвёртый — самые

задачей.

### F-10. Проверенные контроли: обход не найден

**Вердикт: СООТВЕТСТВУЕТ СПЕКЕ.** Эти места проверены и работают; перечислены, чтобы
следующее ревью не тратило на них время.

* `glob.cpp::matchHere` — одиночный `*` **не** пересекает границу сегмента
  (`glob.cpp:104-109`), `**` в конце поглощает остаток пути. Значит
  `%USERPROFILE%\*.*` (правило `user.bigfiles.profile-root`) физически не дотягивается
  до `Documents` и `AppData` — замечание правила верное. Тот же запрет дублируется в
  сборщике: `RootScan::leafAllows` (`candidate_collector.cpp:317-323`) и
  `directChildName` (`:237-253`).
* `**/` совпадает и с нулём сегментов (`glob.cpp:84-88`) — это делает
  `logs.local` (`%LOCALAPPDATA%\**\Logs\**\*.log`) корректным и не «съедающим»
  `%LOCALAPPDATA%\Logs` сверх замысла.
* Неизвестные поля правила и манифеста — ошибка загрузки (`rules.cpp:59-64`,
  `rulesync.cpp:52`), правило не может протащить в модель поле, которого движок не
  проверяет (важно для ADR-008).
* Путь, не описанный ни одним правилом, не удаляется: кандидаты рождаются только
  разворотом правил, а кандидат с `ruleId`, которого нет в наборе, принудительно
  получает `Review` и штраф уверенности (`scoring_bridge::evaluate`) — это §10
  («путь, не совпавший ни с одним известным правилом, никогда не удаляется»).
* `Risky` скрыт по умолчанию и требует второго подтверждения (`plan.cpp:215-219`,
  `cmd_apply.cpp`, слово `DELETE-RISKY`), §12 соблюдён.
* Граница «внутри корня правила» проверяется перед операцией по дескриптору
  (`executor::checkItem`, строка 542 → `vfs_paths::checkRuleRoot`, строка 566), пустой
  корень означает отказ.
* Неразрешённая переменная окружения и относительный локатор делают правило
  неактивным с видимой заметкой, а не ищут путь наугад
  (`candidate_collector.cpp`, `hasUnresolvedVariable`, `isAbsolutePattern`).
* Дубль пути у двух правил считается и попадает в отчёт (`stats.duplicatePaths`) —
  двойного учёта объёма не происходит молча.
* Подпись набора проверяется до применения, при любой ошибке — откат на рабочий
  набор (`rulesync_client.cpp:1420-1450`), §9.2 соблюдён.
* Белый список платформенного слоя закрывает `WinSxS`, `Installer`, `System32`,
  `Program Files`, `System Volume Information` независимо от того, что написано в
  правиле (`vfs_delete.cpp:276-330`) — это единственная причина, по которой
  `winsxs.report` и `installer.cache` не удаляются сегодня (см. F-04).

## 4. Порядок исправлений

1. **F-01** — единственная находка, где теряются данные внутри корня правила.
   Единица операции — отобранные правилом файлы. Плюс тест из F-09.
2. **F-02 + F-03** — вместе это и есть «может ли правило удалить пользовательские
   данные»: пользовательские каталоги не должны ни выбираться по умолчанию, ни
   уходить прямым `Delete`. Три теста.
3. **F-04** — флаг «только оценка» в схеме правил и в планировщике; до этого
   `wsl.vhdx.*` и `npm.pip.cache` остаются правилами, которые можно исполнить.
4. **F-05 + F-06** — белый список корней: один на загрузку правил, один на
   исполнение, с запретом корней пользовательских данных на любом уровне.
5. **F-07** — сохранение решений по правилам, иначе всё вышеперечисленное придётся
   отключать правкой набора на диске.
6. **F-08, F-09** — заметки правил привести в соответствие с поведением; тесты.

## 5. Как проверялось

Ревью статическое по коду плюс прогоны **штатного бинарника** в слоте `a92`. Сборка и
тесты слота — зелёные, чужих файлов не тронуто:

```
cmd.exe /c "tools\build.bat Debug a92"   → [build] ok: build\a92
cmd.exe /c "tools\test.bat Debug a92"    → ALL PASS: 305 проверок, провалов 0
```

Команда `scan` в этой сборке ещё не подключена к адаптеру обхода ФС (об этом сказано
в её справке: возвращает код 4), поэтому кандидаты для прогонов плана составлены вручную
**ровно так, как их выпускает `candidate_collector`** для соответствующих правил
поставки: `path` = корень правила (последний сегмент `**` → корень-каталог),
`allocatedBytes`/`fileCount` = сумма по отобранным файлам, `safety` = уровень из
JSON правила, `confidence` — посчитан по `core/scoring.cpp` и
`scoring_bridge.cpp` (в CLI `plan` уверенность берётся из файла, это видно в
`cmd_apply.cpp::parseCandidate`):

| Кандидат | Расчёт уверенности | Значение |
|---|---|---|
| `user.bigfiles.documents` | 100 − 0 (возраст ≥ 90 дней) − 0 (системный каталог) − 0 (штраф «внутри профиля» только для `safe`) − 0 (шаблон не широкий) − 0 (объём > 64 КБ) | **100** |
| `user.bigfiles.desktop` | то же | **100** |
| `temp.user` | 100 − 15 (внутри профиля и `safe`) | **85** |
| `browser.history.chrome.passwords` | 100 − 20 (широкий шаблон `Login Data*`) | **80** |
| `prefetch.files` | 100 − 0 (времени newestWrite нет → возраст не выдумывается) − 20 (шаблон `*.pf`) − 0 (каталог системный, но `systemRoots` пуст, см. оговорку ниже) | **80** |
| `npm.pip.cache.nuget.packages` | 100 − 0 − 0 − 0 − 0 − 0 | **100** |
| `recycle.bin.allvolumes` | 100 − 0 − 0 − 0 − 0 − 0 (корзина лежит в корне тома, а не в профиле) | **100** |
| `winsxs.report` | 100 − 0 − 0 (системный каталог не распознан) − 0 (локатор без шаблона) | **100** |
| `wsl.vhdx.report.distro.store` | 100 − 0 − 0 − 0 (локатор кончается именем файла) | **100** |

Две оговорки к расчёту — обе про код, а не про числа.

1. `systemRoots` сегодня никто не заполняет: значение приходит от хоста
   (`cmd_scan.hpp:122-126`, «пустые значения означают „не проверено“»), а единственный
   вызов `scoreCandidates` — в `cmd_scan.cpp:911`, и команда `scan` в этой сборке не
   подключена к адаптеру обхода ФС. При пустом `systemRoots` функция
   `scoring_bridge::isInSystemDirectory` возвращает `false` для всего, и системный
   каталог не получает штрафа вовсе: `prefetch.files` — 80 вместо 70,
   `winsxs.report` — 100 вместо 90. Это асимметрия в мосте: для профиля пустое
   значение трактуется пессимистично (`isInsideUserProfile` возвращает `true`, снимаются
   15 баллов), для системных корней — оптимистично. Обе цифры выше порога 50, поэтому
   выводы находок не меняются, но сам штраф за системный каталог сегодня не работает.
2. Для кандидата, у которого `newestWrite` не задан, `makeScoreInput` подставляет
   `context.now`, и блок проверки возраста не выполняется вовсе (нет «моложе порога» —
   нет и штрафа). Для кандидата с `minAgeDays > 0` это честно (сборщик уже отсёк
   молодые файлы), но при ручной сборке списка кандидатов возрастная защита исчезает
   молча.

* прогон 3: `trash review conf 80 Пароли и автозаполнение Chrome`, `trash review conf 80

Чего прогоны **не** доказывают: файлы не удалялись (команды `plan` ничего не трогают,

`vfs::deleteTree`, — а не наблюдением потери файла. Интеграционные тесты, которые
требуют создания каталогов и прав, в этом прогоне не запускались.
