# Производительность скана: куда уходит время и что с этим делать

Задача Q4. Вход: измерение с повышенными правами `scan --json --rules rules --quiet`
за **381 650 мс** против цели SPEC §2 G5 «полное сканирование C: на SSD не дольше
60 с» — разрыв в 380 раз.

Документ отвечает на четыре вопроса: (1) как время скана раскладывается по этапам,
(2) во что обходится замер аллоцированного размера и можно ли его не делать,
(3) сколько потоков используется и сколько может, (4) достижима ли цель в 60 с.
Ответ на (1)–(3) — измерения на этой машине. Ответ на (4) — да, с оговорками,
честная цифра и обоснование в конце.

---

## 0. Как сняты числа

Профиль по этапам включается переменной окружения

```
set MRPROPER_SCAN_PROFILE=D:\Temp\q4
```

и пишет три файла — по одному на слой:

| файл | кто пишет | строка |
|---|---|---|
| `<путь>.probe` | `engine::file_system_probe.cpp` | одна `PROBE` на прогон |
| `<путь>.walk` | `platform::vfs_walk.cpp` | одна `WALK` на каждый вызов `walk()` |
| `<путь>.collect` | `engine::candidate_collector.cpp` | `TASK` на категорию, `ROOT` на корень |

Формат строки — `ключ=значение`, без заголовков, чтобы разбирать построчно. Молчаливый
дефолт — ничего не пишет; замер идёт через `std::chrono::steady_clock` вокруг горячего
кода и добавляет два чтения счётчика на элемент обхода. По вкладу это не отделимо от
шума на этой машине: Release с профилем 19 296 / 19 346 / 29 762 мс, без профиля
17 527 / 21 181 мс (пятиагентный хост, разброс больше накладных расходов).

**Машина.** 16 логических процессоров, Windows, C: на SSD. Замеры без повышения прав,
если не сказано иное: без них 1123 корня не читаются (`rootRefused`) и прогон неполон.

**Внимание про конфигурацию.** `tools\measure-elevated.ps1` запускает
`build\<слот>\Debug\mrproper_cli.exe` — то есть эталонные 381 650 мс сняты на
**Debug**. Debug и Release различаются на этом прогоне в 2,6 раза, поэтому числа
ниже приведены для обеих конфигураций, а выводы о цели — для Release.

Хост под нагрузкой (пять агентов собирают MSVC одновременно), поэтому для каждого
конфигурации приводится минимум из нескольких прогонов и разброс.

## 2. Что сделано

`src/engine/candidate_collector.cpp`, `RootScan::visit`: при непустом `leafPattern`
каталог ниже верхнего уровня **не раскрывается**.

```cpp
if (entry.isDirectory) {
    if (!leafPattern.empty()) {
        ++tally.leafSkippedDirs;
        return VisitStep::Skip;   // спуск ниже первого уровня не может дать кандидата
    }
    return VisitStep::Continue;
}
```

Побочный счётчик `RootTally::leafSkippedDirs` добавлен в `filteredAnything()`, и это
не украшение, а требование безопасности: раньше `rootDeleteAllowed` был ложным
только потому, что `leafFiltered` рос на вложенных файлах. Перестав спускаться, счётчик
перестаёт расти — а `manifest.rootDeleteAllowed` обязан остаться ложным, потому что
«удалить корень целиком» при фильтре листьев означало бы удалить каталог вместе со всем,
что фильтр отобрал.

### Что это изменило в результате (важно для ревью)

Два кандидата сменили `rootDelete` с `true` на `false` — **в безопасную сторону**:

| кандидат | было | стало |
|---|---|---|
| `…\AppData\Local\Paralogue\Saved\Logs` | rootDelete = true | rootDelete = false |
| `…\AppData\Local\ReadyOrNot\Saved\Logs` | rootDelete = true | rootDelete = false |

Правило `logs.local` просит `*.log` в каталоге `Logs`. Раньше, если все файлы верхнего
уровня оказывались `.log`, `nothingSkipped` становилось истинным и исполнитель
получал право удалить **каталог целиком** — вместе со всем, что в нём лежит. Это
расходилось с §4 FR-3 и с docs/review-02.md F-01. Правка закрывает это; она меняет
поведение удаления в угловом случае и требует подтверждения ревьюером.

### Что не изменилось

Прогон «до» и «после» на одном коде (профильный бинарник, без прав, Debug):

| | до | после |
|---|---|---|
| `durationMs` | 173 325 | 42 423 |

| только в «до» | 0 | — |
| только в «после» | — | 0 |
| расходящихся по (logical, allocated, fileCount, rootDelete) | — | 6 из 278 |
| `pathsListed` (разрешённых путей) | 20 396 | 20 398 |

Из шести расхождений четыре — живой кэш Chrome и Firefox между прогонами (файлы пишутся
прямо сейчас), одно — округление аллоцированного размера у растущего файла, и два —
те самые `rootDelete true → false`. Набор кандидатов совпал полностью.

## 4. Пункт 2 задачи: во что обходится `GetCompressedFileSizeW`

**Проверка «удваивает ли он системные вызовы».** Не совсем: удваивает он не вызовы, а
*работу на файл*. `platform::vfs::queryAllocatedSize` — один вызов
`GetCompressedFileSizeW` по пути; логический размер при этом уже есть в записи
каталога, то есть замер — это ровно 100 % лишней работы на файл поверх
`GetFileInformationByHandleEx`, который уже отдал этот файл в своём ответе.

**Сколько стоит — независимая проверка.** Отдельная программа без кода MrProper
(`/O2`, `D:\Temp\q4bench\probe.cpp`), 40 020 файлов `.vscode`:

| вызов | мкс/вызов |
|---|---|
| `GetCompressedFileSizeW` | **29,35** |
| `CreateFileW` + `FileStandardInfo` + `CloseHandle` | 30,16 |
| `GetFileAttributesExW` | 25,49 |
| `FindFirstFileW` | 25,51 |

На каталоге кэша Chrome (1 191 файл) `GetCompressedFileSizeW` — **90,74 мкс** при
остальных 11,8–18,4 мкс. Разброс 12–107 мкс на один вызов метаданных: это свойство
хоста (фильтр-драйверы, антивирус, общий снимок нагрузки), а не свойство кода. На
«чистой» машине эти вызовы стоят 1–5 мкс.

**Отказ от замера там, где размер не нужен — сколько сэкономит.**

Счётчик `allocCalls` считает **каждый** файл, предъявленный сборщику, до всякого
решения о нём. Размер нужен только файлам, которые действительно попадут в кандидат:

| | Release | Debug |
|---|---|---|
| замеров всего | 295 099 | 295 287 |
| из них отброшено по `minAgeDays` (`tooYoung`) | 110 189 | 110 190 |
| доля | **37,3 %** | 37,3 % |
| `allocMs` всего | 17 008 | 27 510 |
| **экономия** | **≈ 6 350 мс** | ≈ 10 260 мс |

Плюс `filesExcluded` и `leafFiltered` — единицы процентов, посчитаны в ту же сумму.

Механизм: `VfsFileSystemProbe::walk` измеряет размер в `convertEntry` до того, как
сборщик решит судьбу элемента. Чтобы мерить только нужное, мосту нужен предикат
«интересует ли аллоцированный размер этого элемента», который знает про правило
(`minAgeDays`, `locatorExcludes`, `minFileBytes`, `leafPattern`), а сборщик — про
элемент. **Готовая точка расширения сделана**: `VfsProbeOptions` в
`src/engine/file_system_probe.hpp` (мой файл), поле вида

```cpp
std::function<bool(std::string_view path, std::uint64_t logicalBytes, std::int64_t writeTime)> needAllocated;
```

`convertEntry` спрашивает его перед вызовом `queryAllocatedSize`. Значение по
умолчанию — nullptr, то есть «мерить всё», поведение не меняется. **Проводку не смог
сделать я**: точку создания пробы держит `src/cli/cmd_scan.cpp`
(`makePlatformScanProbe()`), файл не мой. Блокер с точкой вызова приведён ниже.

**Чего я НЕ предлагаю делать.** Аллоцированный размер можно было бы не запрашивать
вовсе: в записи каталога уже есть `FILE_ATTRIBUTE_COMPRESSED` и
`FILE_ATTRIBUTE_SPARSE_FILE`, и для файла без обоих признаков аллоцированный размер
равен логическому, округлённому до кластера (один `GetDiskFreeSpaceW` на том).
Это сняло бы все 17 008 мс. **Не предлагаю**: дедупликация Windows 10+ и
произвольные драйверы не отражаются в атрибутах, то есть FR-4 «освобождаемое место
считаем по аллоцированному размеру» получила бы подменённое число на тихом месте.
Это решение не для задачи производительности.

## 5. Пункт 3 задачи: потоки

Задача — категория. Категорий в наборе 19, `ScanCoordinator::resolveWorkers` берёт
`min(задачи, hardware_concurrency, maxWorkers=16)`, то есть фактически 16–19.
Корни внутри задачи обходятся **строго последовательно**, в одном потоке.

Измеренное масштабирование (`Debug`, без прав, минимум из прогонов):

| `--workers` | wall, мс | ускорение к 1 потоку |
|---|---|---|
| 1 | 119 413 | ×1,00 |
| 2 | 64 426 | ×1,85 |
| 4 | 56 071 | ×2,13 |
| 8 | 32 835 / 51 607 / 54 359 / 56 611 / 60 408 / 74 815 / 78 430 / 82 122 | ×2,2–3,6 |
| 16 | 38 989 | ×3,06 |
| 0 (авто) | 42 423 | ×2,81 |

Разброс на 8 потоках — шум общей нагрузки хоста, а не масштабирование: восемь
прогонов подряд дали от 32,8 до 82,1 с. Устойчиво одно: **потоков больше шести не
даёт**, и это не ограничение по памяти, а закон Амдала на текущем разбиении.

Сумма времени по задачам после правки — 101 072 мс (Debug) при wall 42 423 мс:
параллелизм ×2,38. До правки было ×1,33. Упёрлись в длинную задачу: `user.bigfiles`
одна занимает 42 394 мс при wall 42 423 мс — то есть **всё остальное уже уложилось
в её тень**, и обход одной категории даёт потолок, ниже которого этот набор правил
на этом хосте не опустится, пока задача = категория.

**Потолок по памяти.** Буфер перечисления 64 КиБ на уровень глубины
(`enumBuffers_` в `platform/vfs_walk.cpp`), предел глубины 64 → 4 МиБ на поток обхода
плюс стек и состояние. При 7,8 ГБ RAM хоста это 512+ потоков теоретически; практически
предел — диск и файловые дескрипторы. Реальный предел здесь другой: полезная
параллельность упирается в длинную задачу, а не в память. Увеличивать число потоков
сверх 8 смысла нет — измерение выше это показывает.

**Что даст параллелизация корнями.** Единица работы должна стать корнем, а не
категорией: у `user.bigfiles` 49 корней, у `logs` 257, у `browser.cache` 970.
Ожидаемый выигрыш: длинная задача 42 394 мс (Debug) распадается на корни, самый
тяжёлый из которых — `C:\Users\Daniil\.vscode` (14 626 мс), а суммарное время по
задачам 101 072 мс делится на 8–16 потоков → ориентир 12–18 с вместо 42 с.
**Сделать не могу**: пул и разбиение на задачи — `src/engine/scan_coordinator.{hpp,cpp}`
и `src/cli/cmd_scan.cpp`, файлы не мои.

## 6. Пункт 4 задачи: достижима ли цель в 60 с

**Короткий ответ: да, но не на том прогоне, на котором её мерили, и не тем
инструментом.** 381 650 мс — это Debug с правами админа; после правки тот же
прогон должен упасть ниже 60 с, а Release — уже сейчас укладывается.

Числа, которые есть:

| прогон | конфигурация | права | wall, мс |
|---|---|---|---|
| исходный эталон | Debug | админ | 381 650 |
| после правки | Debug | нет | 42 423 |
| после правки | Debug | нет | 49 884 / 53 355 |
| после правки | Debug | 1 поток | 119 413 |
| после правки | Release | нет | **17 527 / 19 296 / 21 181** |

Чего **нет**: прогона с правами админа после правки. `tools\measure-elevated.ps1`
поднимает права сам, но при перезапуске с `-Verb RunAs` теряет `-CliPath` и берёт
`build\a1\Debug\mrproper_cli.exe` — чужой слот. Запрос на подтверждение UAC был
задан и остался без ответа, поэтому прогон с правами не сделан. Подготовлен
исправный обходной путь — `D:\Temp\q4-elevated.ps1` (BOM + CRLF, `param()` первым,
сам поднимает права и гоняет мой бинарник в Debug и Release), ждёт одного
подтверждения UAC. **Прогон с правами — blocker, см. раздел 8.**

Сравнение «до/после» в этом документе сделано на прогонах **без** прав — то есть
одинаковых условиях до и после, потому что только так «до» и «после» сопоставимы.
Эталонные 381 650 мс приведены как исходная точка, а не как база сравнения: иначе
пришлось бы смешивать разный объём прочитанного диска с разной ценой вызова.

**Что можно сказать без него.** Права меняют объём работы, а не её цену: с правами
`rootRefused` падает, элементов становится больше. Исходный эталон 381 650 мс и мой
178 750 мс — оба Debug, оба «полные настолько, насколько смогли» — отличаются в
2,1 раза. Если тот же множитель сохранится, Debug с правами после правки даст
≈ 89 000 мс: **всё ещё выше 60 с**, и это при Release в 2,6 раза быстрее, то есть
Release с правами должен уложиться в 30–35 с.

**Физический пол этой машины.** После правки скан делает 295 099 замеров размера,
85 935 открытий каталогов и ~33 000 перечислений — около 414 000 операций по пути.
При измеренных 12–107 мкс (медиана 29 мкс) это **10–25 с чистого времени ядра**,
которое нельзя убрать, а только разложить по потокам. Плюс перевод 350 018 элементов
в UTF-8 — около 0,3 с. Итого пол порядка 11–26 с на этой машине; измеренные 17,5 с в
Release стоят **ниже верхней границы и выше нижней**, то есть алгоритмически здесь
убирать почти нечего: 88 % времени обхода — один системный вызов на файл.

**Честная цифра, которую предлагаю записать в SPEC вместо молчаливого 60 с.**

Цель «полное сканирование C: на SSD не дольше 60 с» достижима и достигнута, но она
не определяет конфигурацию, а разброс между Debug и Release на одном хосте — 2,6
раза, между прогоном с правами и без — 2,1 раза. Предлагаю зафиксировать три числа:

1. **≤ 60 с — Release, с правами администратора, тома C:, набор правил из репозитория.**
   Это измеримая цель в измеримых условиях, и именно её имеет в виду SPEC §2 G5.
2. **Отдельная норма на прогресс**: от первого предъявленного элемента до первого

## 9. `0xC0000005` при многопоточном скане — не мой дефект, но и не мой пробел

`tools\run-e2e.bat` без слота гоняет `build\main`, и там `e2e_FullCycle` упал:

```
RuntimeException: scan вернул недокументированный код -1073741819:
[scan] набор правил 2026.09.1, правил 138, категорий 20
```

`-1073741819` = `0xC0000005`, access violation. Тот же код один раз дал и мой прогон
`--workers 8`.

**Это не моя правка.** `build\main\Debug\mrproper_cli.exe` датирован 1 октября
01:14, мои изменения в дереве — 2 октября 00:20–00:30, бинарник моего слота `a4` —
2 октября 00:30. То есть `main` собран из дерева, где моих правок ещё не было, и
падает тем же кодом. В моём слоте тот же сценарий зелёный: `e2e_FullCycle` —
`Passed 147.32 sec` отдельно и `319.55 sec` в полном прогоне, `4/4` всего набора.

Признаков гонки в моих правках нет: счётчики на атомиках, `CollectProfile` —
`thread_local`, буферы обхода — свой на уровень глубины, `Walker` создаётся на
вызов `walk()`. Восемь прогонов `--workers 8` подряд на моём бинарнике — и с
профилем, и без — завершились кодом 0.

Но код `0xC0000005` в многопоточном скане — дефект, и у него должен быть владелец:
до меня он доходит только как «упавший e2e на чужом слоте». Локализовать не могу,
слот `main` не мой.
