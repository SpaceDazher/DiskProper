# MrProper

Утилита для Windows: показывает все диски и разделы, находит, что можно безопасно
освободить, и чистит это с возможностью отмены. Аналог CCleaner, но с акцентом на
прозрачность: каждая позиция объяснена, у каждой есть уровень риска, всё удалённое
можно вернуть.

Спецификация проекта — [docs/SPEC.md](docs/SPEC.md). Это основной документ: архитектура,
модель данных, этапы, риски и критерии приёмки. Код обязан соответствовать спеке, а не
наоборот.

## Текущее состояние

Проект в разработке, версии ещё нет. Сделано:

- ядро `src/core` — JSON, glob-сопоставление, форматирование, модель, загрузка и
  валидация правил очистки, скоринг кандидатов;
- слой Windows `src/platform` — разделы и тома, обход ФС с длинными путями и reparse-точками,
  Restart Manager, собственная корзина с журналом транзакций;
- движок `src/engine` — план операций, исполнитель очистки, отмена и восстановление;
- CLI `mrproper-cli` для CI и e2e: `disks`, `scan`, `plan`, `apply`, `report`, `rules`;
- интерфейс на Win32 + Direct2D;
- правила очистки по категориям в `rules/*.json`.

Чего пока нет: модуля SMART/NVMe (запланирован на v1.1), сервиса и планировщика (v1.2),
реестра и автозагрузки (v2.0).

**Приёмка MVP не пройдена: из 12 критериев §12 `docs/SPEC.md` полностью закрыты два.**
Остальные десять: шесть «частично», одно «не выполнено», три «не проверено» — и все три
непроверенных упираются в среду, а не в код: права администратора и три эталонные VM
(§12.1), тайминги скана C: SSD (§12.2), чистая VM для установщика (§12.10). На этой
машине закрыть их нечем. Полный разбор — `docs/dod-checklist.md`, список незакрытых
строк — `docs/defects.md` (открыто 43 строки, закрыто 26).

Что зелёно на 2026-10-01 (прогон приёмки P4, слот `a4`): сборка Debug и Release без
предупреждений при `/W4 /WX`, юит **320/0** и интеграционные **31/0** в обеих
конфигурациях, ворота окна — код 0 в **7 конфигурациях из 7**, e2e — 4 из 4 (990,96 с,
последний прогон). Что не зелёно: `clang-tidy` даёт **292 находки** на 34 единицах
компиляции, каталог локализации не проверяется ни одним тестом, у приложения **нет файла
лога**, а на экране «Настроек» обрезан столбец и печатается «Правил: 138 файлов»
(**D-70**, **D-71**).

## Сборка и тесты

Требуется Visual Studio Build Tools с C++ workload и CMake. Скрипты находят компилятор
сами: `build.bat` и `test.bat` пробуют `D:\BuildTools\VC\Auxiliary\Build\vcvars64.bat`,
затем `vswhere`, затем известные пути VS 2019/2022.

### Проверка одной командой: какой она реально является

Скрипта «проверить всё» в проекте **нет**, и это не недоработка оформления, а решение:
полный набор ворот занимает больше получаса (e2e — 16,5 минуты, clang-tidy — 11, окно —
две минуты и требует, чтобы передний план был свободен), и одна команда, которая
полчаса молчит, а потом падает на e2e, хуже трёх коротких, чем можно пользоваться
по отдельности.

**Базовое (это и есть критерий приёмки):**

```bat
tools\build.bat Debug a4
cmd.exe /c "tools\test.bat Debug a4"
```

**Полное (что реально запускалось в прогоне P4, слот `a4`, 2026-10-01):**

| Ворота | Команда | Время | Итог того дня |
| --- | --- | --- | --- |
| Сборка Debug | `tools\build.bat Debug a4` | 92 с | код 0, 0 предупреждений |
| Сборка Release | `tools\build.bat Release a4` | 63 с | код 0, 0 предупреждений |
| Юит + интеграционные, Debug | `cmd.exe /c "tools\test.bat Debug a4"` | 4 с | **320/0** и **31/0**, код 0 |
| Юит + интеграционные, Release | `tools\test.bat Release a4` | 2 с | **320/0** и **31/0**, код 0 |
| Ворота окна, 7 конфигураций | `tools\ui-smoke.ps1` × 7 (см. ниже) | 118 с | **7 кодов 0 из 7** |
| E2E на Pester 4.x | `set MRPROPER_PESTER_MODULE=…` + `tools\test.bat Debug a4 e2e` | 991 с | 4/4 (числа прогона N4) |
| `clang-tidy` | `powershell -File tools\run-tidy.ps1 -Slot a1 -Config Release` | 644 с | **292 находки**, 0 ошибок |

`test.bat` собирает **ничего** — перед ним обязателен `tools\build.bat`. Что делает
`test.bat` без явного набора:

| Ворота | Что запускается | Ожидаемый вывод | Что это доказывает |
| --- | --- | --- | --- |
| 1. Ядро | `mrproper_unit_tests.exe` | `ALL PASS: 320 проверок, провалов 0` | JSON, glob, единицы, правила, скоринг, план, отчёты, отмена, синхронизация правил |
| 2. Win32-слой | `mrproper_integration_tests.exe` | `ALL PASS: 31 проверок, провалов 0` | реальные файлы в `%TEMP%`: границы корня правила, корзина и её транзакции, длинные пути, reparse, обход ФС |

На 2026-10-01 оба набора зелёные в обеих конфигурациях. **Одна оговорка, которая не
устарела:** D-56 («механизм удаления по разрешённому списку») формально не
воспроизводится, но правка, которая это дала, не зафиксирована отдельным коммитом, и
повторяемость не проверена — «перестало воспроизводиться» не то же, что «исправлено».

Обе строки чисел обязаны совпадать с `docs/build-report.md`. Если расходятся — верен
фактический вывод, а не документ.

**Осторожно: `test.bat` врёт в зелёную сторону.** Если интеграционный бинарник не
собран (например, сборка отказалась), `test.bat` печатает «интеграционные тесты не
собраны … пропущен» и **возвращает код юит-набора**, то есть 0 при неполном прогоне.
Код 0 от `test.bat` означает «оба набора зелёные» только если в выводе есть строка
`== MrProper integration ==` и `ALL PASS`. Это открытый дефект **D-58**.

Вторая оговорка, свежая: **числа ворот окна не воспроизводятся как числа.** Конфигурация
«как есть» наследует `HKCU\Software\MrProper\UI` (`nav.current`, `window.placement`), и
в одном батче из семи прогонов вернула два разных окна — 1280x720 и 1136x795 — при
одинаковой команде. Надёжно воспроизводится только «код 0» и «окно нарисовано»
(**D-67**).

Отдельные наборы и фильтры:

```bat
tools\build.bat Debug a4                 :: конфигурация + сборка слота a4
tools\test.bat  Debug a4 unit            :: только ядро
tools\test.bat  Debug a4 integration     :: только Win32-слой
tools\test.bat  Debug a4 unit walk_      :: фильтр по префиксу имени проверки
tools\build.bat Release a4               :: релизная сборка
tools\test.bat  Release a4               :: оба набора в Release
tools\run-e2e.bat Debug a4               :: e2e на Pester 4.x, минуты
tools\run-e2e.bat Debug a4 e2e_FullCycle :: один сценарий
```

**Ворота окна — семь конфигураций (команды прогона P4).** Первые шесть на Debug, седьмая
на Release:

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -Width 1280 -Height 720
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -Width 1920 -Height 1080
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -Width 1280 -Height 720 -DpiPercent 150
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -ThemeMode light -ExpectBackground light
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -ThemeMode dark  -ExpectBackground dark
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Release\mrproper.exe
```

**Обход всех пяти страниц** добавляет ключ `-AllPages` и меряет раскладку каждой
страницы (размер элементов и попадание прямоугольников в клиентскую область):

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui-smoke.ps1 -Exe build\a4\src\ui\Debug\mrproper.exe -AllPages -Width 900 -Height 600
```

**Этот ключ крадёт фокус машины.** Он переключает страницы настоящими клавишами
`Ctrl+1…5` через `keybd_event`, и при чужом переднем окне `SetForegroundWindow` вернёт
false, а ворота честно отдадут код **11** — «обход не состоялся». На машине, где открыто
что-то ещё, его запускать нельзя: это не «медленнее», это бессмысленно.

**Слот — обязателен.** `a4` выше — каталог сборки `build\a4`. Пять агентов, гоняющих
общий `build\Debug`, портят кэш CMake друг другу; плюс сама компиляция сериализована
замком `tools\build_lock.ps1` — на хосте 7.8 ГБ RAM пять параллельных `cl.exe` дают OOM.

**e2e идёт минуты и по умолчанию не входит в `test.bat` без набора.** Нужен Pester **4.x**;
встроенный в Windows PowerShell 5.1 Pester 3.4 и Pester 5 не подходят — сценарии написаны
на форматах 4.x:

```bat
set MRPROPER_PESTER_MODULE=D:\Tools\Pester\4.10.1\Pester.psd1
tools\run-e2e.bat Debug a4
```

Ключ `-Destructive` не передаётся **никогда**: на рабочей машине за ним реальный кэш
пользователя, а не тестовые данные. Настоящее удаление и восстановление проверяются
только на песочнице в `%TEMP%` с отдельным каталогом правил.

**Ошибки ворот, которые не оставляют ложного «зелёного»:** `build.bat` и `test.bat` кодом
`9009` отвечают «не найден `vcvars64.bat`» — это отсутствие тулчейна, а не зелёный прогон;
`test.bat` кодом `2` отвечает «бинарники не собраны» или «нет Pester 4.x»; набор
интеграционных тестов кодом `1` отвечает «проверки провалились». Единственное исключение
из этого правила — отсутствие интеграционного бинарника, см. абзац выше: там код 0 при
неполном прогоне, и это D-58.

Из WSL то же самое:

```bash
cmd.exe /c "tools\\build.bat Debug a4"
cmd.exe /c "tools\\test.bat Debug a4"
```

Ядро переносимо: его можно собрать и проверить и на Windows, и в Linux — в нём нет
Windows API. Это сделано намеренно, чтобы правила и скоринг тестировались на любом хосте
(ADR-004).

## Ограничения инструмента

- **Карта разделов требует прав администратора.** `\\.\PhysicalDriveN` без повышения не
  открывается, и `mrproper-cli disks` отдаёт пустую карту с кодом `3`. Это не дефект
  сборки, а следствие FR-6: инструмент не просит права сам.
- **Сборки не подписаны** (ADR-009). Windows SmartScreen покажет «неизвестный издатель» —
  это ожидаемо. Сертификата подписи нет, утилита личная.
- **Реальное удаление и восстановление проверены только на песочнице.** Настоящий `%TEMP%`
  пользователя, AppData, кэши браузеров и `ProgramData` сценарии не трогают.
- **Эталонных VM нет.** Три виртуальные машины (MBR/BIOS, GPT/UEFI, мультидиск) для §12.1
  и чистая VM для проверки установщика §12.10 в этом репозитории не описаны и не
  приложены. Из-за них три пункта §12 остаются непроверенными, и закрыть их на этой
  машине нечем.
- **`clang-tidy` запускается, но не чист.** `tools\run-tidy.ps1` собирает базу компиляции
  через Ninja + clang-cl (генератор Visual Studio `compile_commands.json` не пишет) и
  даёт **292 находки на 34 единицах компиляции за 644 с, 0 ошибок компиляции**. §12.8
  требует «чист», то есть до зелёного ещё 284 замечания.
- **Санитайзеры на этом тулчейне не работают.** Рантайм ASan на v142 не
  инициализируется, поэтому часть §12.8 не проверяется в принципе. `/W4 /WX` при этом
  включены и держатся: 0 предупреждений в Debug и Release.
- **У приложения нет файла лога.** `Logger::open()` не вызывается ни разу — есть только
  кольцевой буфер в памяти, поэтому «лог с путём и HRESULT» (§12.7) живёт наполовину.
- **Скрипта «проверить всё» нет.** Базовое — `tools\build.bat` + `tools\test.bat`, см.
  раздел выше; окно, e2e и clang-tidy — отдельные точки входа со своими требованиями.

## Правила очистки — данные, а не код

Правила лежат в `rules/*.json` и обновляются без пересборки приложения. Каждая
категория имеет уровень риска (`safe`, `review`, `risky`), минимальный возраст файлов
и объяснение. Правила, скачанные из сети, проверяются по подписи и SHA-256; при любом
несовпадении приложение продолжает работать на предыдущем рабочем наборе (ADR-008).

Как добавить свою категорию — [docs/rules-authoring.md](docs/rules-authoring.md).

## Принципы, которые нельзя нарушать

1. **Ничего не удаляется без объяснения.** У каждой позиции есть причина, объём и
   уровень риска. `risky` по умолчанию скрыты.
2. **Путь проверяется дважды.** Кандидат удаляется, только если он лежит внутри корня
   своего правила (после разрешения символьных ссылок и коротких имён).
3. **Обратимость.** Собственная корзина приложения с журналом транзакций, а не
   системная корзина: она не ограничена по размеру и даёт честную транзакцию.
4. **Никакой телеметрии.** Данные не покидают машину. Наружу уходит только отчёт,
   который вы формируете сами.

## Что этот проект НЕ умеет

Короткий список без смягчений. Полный — `docs/team-report.md` §9.

1. **Не видит разделов без прав администратора.** `\\.\PhysicalDriveN` не открывается,
   `disks` отдаёт пустую карту и код 3. Право повысить один раз можно, но на этой машине
   не подтверждалось.
2. **Не проверен ни на одной эталонной VM** (MBR/BIOS, GPT/UEFI, мультидиск) и **ни на
   чистой VM** для установщика. Всё, что касается геометрии разделов и установки, написано
   и не проверено ни разу.
3. **Не удаляет по-настоящему на машине человека.** Ключ `-Destructive` не передаётся
   никогда; настоящее удаление и восстановление проверены только на песочнице в `%TEMP%`.
4. **Не пишет лог на диск** — `Logger::open()` не вызывается ни разу, есть только
   кольцевой буфер в памяти.
5. **Не измеряет свою полноту локализации в воротах.** `selfCheck()` не зовёт ни один тест.
   Сегодня каталог полон (352 ключа, 0 пустых, 0 дублей, 0 непереведённых), но это
   посчитано вручную, а не защищено проверкой.
6. **Не проходит `clang-tidy` начисто:** 292 находки, из них 247 — одна отключённая
   проверка на одной строке; остаётся 284 замечания до критерия «чист».
7. **Не работает с санитайзерами** на этом тулчейне и **не проверен на настоящих 150 % DPI** —
   только эмуляция сообщения о смене DPI, которая двигает геометрию, но не масштаб системы.
8. **Не проверен ни на чужом компиляторе, ни на Windows 10.** Всё зелёное здесь зелено на
   одном хосте: Windows 11, MSVC v142/v143, `/W4 /WX`.
9. **«Правил: 138 файлов»** — да, на экране «Настроек» счётчик правил печатается с единицей
   измерения «файлы» (**D-70**), и третий столбец списка правил обрезан (**D-71**).
   Это открытые дефекры, а не особенности сборки.
