# MrProper

Утилита для Windows: показывает все диски и разделы, находит, что можно безопасно
освободить, и чистит это с возможностью отмены. Аналог CCleaner, но с акцентом на
прозрачность: каждая позиция объяснена, у каждой есть уровень риска, всё удалённое
можно вернуть.

Спецификация проекта — [docs/SPEC.md](docs/SPEC.md). Это основной документ: архитектура,
модель данных, этапы, риски и критерии приёмки. Код обязан соответствовать спеке, а не
наоборот.

## Текущее состояние

Проект в разработке, версии ещё нет. Сделано:

- ядро `src/core` — JSON, glob-сопоставление, форматирование, модель, загрузка и
  валидация правил очистки, скоринг кандидатов;
- слой Windows `src/platform` — разделы и тома, обход ФС с длинными путями и reparse-точками,
  Restart Manager, собственная корзина с журналом транзакций;
- движок `src/engine` — план операций, исполнитель очистки, отмена и восстановление;
- CLI `mrproper-cli` для CI и e2e: `disks`, `scan`, `plan`, `apply`, `report`, `rules`;
- интерфейс на Win32 + Direct2D;
- правила очистки по категориям в `rules/*.json`.

Чего пока нет: модуля SMART/NVMe (запланирован на v1.1), сервиса и планировщика (v1.2),
реестра и автозагрузки (v2.0).

**Приёмка MVP не пройдена: из 12 критериев §12 `docs/SPEC.md` полностью закрыты два.**
На 2026-09-30 второй набор интеграционных тестов красный (4-5 провалов из 31, число
нестабильно между прогонами), то есть
путь «удалить по разрешённому списку» не работает. Полный разбор —
`docs/dod-checklist.md`, список незакрытых строк — `docs/defects.md`. Не закрыты также
критерии, требующие эталонных VM, прав администратора, чистой VM и ручного прогона
интерфейса: их на этой машине закрыть нечем.

## Сборка и тесты

Требуется Visual Studio Build Tools с C++ workload и CMake. Скрипты находят компилятор
сами: `build.bat` и `test.bat` пробуют `D:\BuildTools\VC\Auxiliary\Build\vcvars64.bat`,
затем `vswhere`, затем известные пути VS 2019/2022.

### Одна команда: всё, что можно проверить на этой машине

```bat
tools\test.bat Debug a3
```

Это и есть ворота проекта. Команда собирает **ничего**, поэтому перед ней обязателен
`tools\build.bat Debug a3`. Всё, что делает `test.bat` без явного набора:

| Ворота | Что запускается | Ожидаемый вывод | Что это доказывает |
| --- | --- | --- | --- |
| 1. Ядро | `mrproper_unit_tests.exe` | `ALL PASS: 320 проверок, провалов 0` | JSON, glob, единицы, правила, скоринг, план, отчёты, отмена, синхронизация правил |
| 2. Win32-слой | `mrproper_integration_tests.exe` | `ALL PASS: 31 проверок, провалов 0` | реальные файлы в `%TEMP%`: границы корня правила, корзина и её транзакции, длинные пути, reparse, обход ФС |

**На 2026-09-30 второй набор красный:** `FAIL: 31 проверок, провалов 4-5`, код возврата 1.
Провалы — в семействе `executor_manifest_*`, то есть в пути «удалить по разрешённому
списку»: 0 файлов удалено, `hr=0x80070005`. Число **нестабильно**: восемь прогонов подряд
дали 5, 5, 5, 4, 5, 5, 5, 4 — четыре проверки красные всегда, пятая то красная, то зелёная. Это открытая P0 **D-56**, разбор
— `docs/defects.md` §3.11.2. Первое число выше — фактическое, второе — то, что должно
стать фактическим.

Обе строки чисел обязаны совпадать с `docs/build-report.md`. Если расходятся — верен
фактический вывод, а не документ.

**Осторожно: `test.bat` врёт в зелёную сторону.** Если интеграционный бинарник не
собран (например, сборка отказалась), `test.bat` печатает «интеграционные тесты не
собраны … пропущен» и **возвращает код юит-набора**, то есть 0 при неполном прогоне.
Код 0 от `test.bat` означает «оба набора зелёные» только если в выводе есть строка
`== MrProper integration ==` и `ALL PASS`. Это открытый дефект **D-58**.

Отдельные наборы и фильтры:

```bat
tools\build.bat Debug a3                 :: конфигурация + сборка слота a3
tools\test.bat  Debug a3 unit            :: только ядро
tools\test.bat  Debug a3 integration     :: только Win32-слой
tools\test.bat  Debug a3 unit walk_      :: фильтр по префиксу имени проверки
tools\build.bat Release a3               :: релизная сборка
tools\test.bat  Release a3               :: оба набора в Release
tools\run-e2e.bat Debug a3               :: e2e на Pester 4.x, минуты
tools\run-e2e.bat Debug a3 e2e_FullCycle :: один сценарий
```

**Слот — обязателен.** `a3` выше — каталог сборки `build\a3`. Пять агентов, гоняющих
общий `build\Debug`, портят кэш CMake друг другу; плюс сама компиляция сериализована
замком `tools\build_lock.ps1` — на хосте 7.8 ГБ RAM пять параллельных `cl.exe` дают OOM.

**e2e идёт минуты и по умолчанию не входит в `test.bat` без набора.** Нужен Pester **4.x**;
встроенный в Windows PowerShell 5.1 Pester 3.4 и Pester 5 не подходят — сценарии написаны
на форматах 4.x:

```bat
set MRPROPER_PESTER_MODULE=D:\Tools\Pester\4.10.1\Pester.psd1
tools\run-e2e.bat Debug a3
```

Ключ `-Destructive` не передаётся **никогда**: на рабочей машине за ним реальный кэш
пользователя, а не тестовые данные. Настоящее удаление и восстановление проверяются
только на песочнице в `%TEMP%` с отдельным каталогом правил.

**Ошибки ворот, которые не оставляют ложного «зелёного»:** `build.bat` и `test.bat` кодом
`9009` отвечают «не найден `vcvars64.bat`» — это отсутствие тулчейна, а не зелёный прогон;
`test.bat` кодом `2` отвечает «бинарники не собраны» или «нет Pester 4.x»; набор
интеграционных тестов кодом `1` отвечает «проверки провалились». Единственное исключение
из этого правила — отсутствие интеграционного бинарника, см. абзац выше: там код 0 при
неполном прогоне, и это D-58.

Из WSL то же самое:

```bash
cmd.exe /c "tools\\build.bat Debug a3"
cmd.exe /c "tools\\test.bat Debug a3"
```

Ядро переносимо: его можно собрать и проверить и на Windows, и в Linux — в нём нет
Windows API. Это сделано намеренно, чтобы правила и скоринг тестировались на любом хосте
(ADR-004).

## Ограничения инструмента

- **Карта разделов требует прав администратора.** `\\.\PhysicalDriveN` без повышения не
  открывается, и `mrproper-cli disks` отдаёт пустую карту с кодом `3`. Это не дефект
  сборки, а следствие FR-6: инструмент не просит права сам.
- **Сборки не подписаны** (ADR-009). Windows SmartScreen покажет «неизвестный издатель» —
  это ожидаемо. Сертификата подписи нет, утилита личная.
- **Реальное удаление и восстановление проверены только на песочнице.** Настоящий `%TEMP%`
  пользователя, AppData, кэши браузеров и `ProgramData` сценарии не трогают.
- **Эталонных VM нет.** Три виртуальные машины (MBR/BIOS, GPT/UEFI, мультидиск) для §12.1
  и чистая VM для проверки установщика §12.10 в этом репозитории не описаны и не
  приложены.
- **`clang-tidy` и санитайзеры не идут в ворота.** Генератор Visual Studio не пишет
  `compile_commands.json`, поэтому `clang-tidy` запустить нечем; рантайм ASan на v142 не
  инициализируется. `/W4 /WX` при этом включены и держатся.

## Правила очистки — данные, а не код

Правила лежат в `rules/*.json` и обновляются без пересборки приложения. Каждая
категория имеет уровень риска (`safe`, `review`, `risky`), минимальный возраст файлов
и объяснение. Правила, скачанные из сети, проверяются по подписи и SHA-256; при любом
несовпадении приложение продолжает работать на предыдущем рабочем наборе (ADR-008).

Как добавить свою категорию — [docs/rules-authoring.md](docs/rules-authoring.md).

## Принципы, которые нельзя нарушать

1. **Ничего не удаляется без объяснения.** У каждой позиции есть причина, объём и
   уровень риска. `risky` по умолчанию скрыты.
2. **Путь проверяется дважды.** Кандидат удаляется, только если он лежит внутри корня
   своего правила (после разрешения символьных ссылок и коротких имён).
3. **Обратимость.** Собственная корзина приложения с журналом транзакций, а не
   системная корзина: она не ограничена по размеру и даёт честную транзакцию.
4. **Никакой телеметрии.** Данные не покидают машину. Наружу уходит только отчёт,
   который вы формируете сами.
